# Conceito principal

Uma operação **stateless** consegue processar os registros atuais sem depender de informações mantidas de micro-batches anteriores.

Exemplo:

```python
df.filter(F.col("value") >= 100)
```

Já uma operação **stateful** precisa manter informações intermediárias para continuar corretamente o processamento nos micro-batches seguintes.

Exemplo:

```python
df.groupBy("customer_id").agg(
    F.sum("value").alias("total_value")
)
```

Neste caso, para calcular um valor acumulado, o Spark precisa saber o que já havia sido calculado anteriormente para cada `customer_id`.

Conceitualmente:

```text
Batch 1
A → 100
B → 50
   ↓
STATE
A → 100
B → 50

Batch 2
A → 30
C → 70
   ↓
STATE atualizado
A → 130
B → 50
C → 70
```

# Experimento A - Stateless vs Stateful

## Objetivo

Comparar uma operação stateless com uma operação stateful e observar as diferenças nas métricas expostas pelo Structured Streaming.

---

## Dados

Fonte criada com quatro registros:

```text
A → 100
A → 50
B → 200
C → 80
```

---

## Setup

```python
from pyspark.sql import functions as F

sourceA = "workspace.default.lab29_source_a"
target_stateless = "workspace.default.lab29_stateless_a"
target_stateful = "workspace.default.lab29_stateful_a"

checkpoint_stateless = "/Volumes/workspace/default/lab29_volume/checkpoint_a_stateless"
checkpoint_stateful = "/Volumes/workspace/default/lab29_volume/checkpoint_a_stateful"

spark.sql(f"DROP TABLE IF EXISTS {sourceA}")
spark.sql(f"DROP TABLE IF EXISTS {target_stateless}")
spark.sql(f"DROP TABLE IF EXISTS {target_stateful}")

dbutils.fs.rm(checkpoint_stateless, True)
dbutils.fs.rm(checkpoint_stateful, True)

data = [
    ("A", 100.0),
    ("A", 50.0),
    ("B", 200.0),
    ("C", 80.0)
]

df = spark.createDataFrame(
    data,
    ["customer_id", "value"]
)

df.write \
    .format("delta") \
    .mode("overwrite") \
    .saveAsTable(sourceA)

display(spark.table(sourceA))
```

### Observação sobre os nomes das tabelas

As linhas:

```python
sourceA = "workspace.default.lab29_source_a"
target_stateless = "workspace.default.lab29_stateless_a"
target_stateful = "workspace.default.lab29_stateful_a"
```

apenas criam variáveis Python contendo nomes de tabelas.

A tabela é criada de fato somente quando ocorre uma escrita, por exemplo:

```python
df.write.saveAsTable(sourceA)
```

---

## Experimento A1 - Operação Stateless

### Transformação

```python
df_stream_stateless = (
    spark.readStream
    .format("delta")
    .table(sourceA)
)

df_filtered = (
    df_stream_stateless
    .filter(F.col("value") >= 100)
)
```

### Action

```python
query_stateless = (
    df_filtered.writeStream
    .format("delta")
    .outputMode("append")
    .option("checkpointLocation", checkpoint_stateless)
    .trigger(availableNow=True)
    .toTable(target_stateless)
)

query_stateless.awaitTermination()
```

### Resultado

```text
A → 100
B → 200
```

O filtro manteve somente os registros com `value >= 100`.

---

## Métricas observadas - Stateless

```python
for p in query_stateless.recentProgress:
    print("batchId:", p.batchId)
    print("inputRows:", p.numInputRows)
    print("stateOperators:", p.stateOperators)
```

Saída observada:

```text
batchId = 0
numInputRows = 2
stateOperators = []
```

### Interpretação

#### `batchId = 0`

Representa o primeiro micro-batch executado por essa query.

#### `numInputRows = 2`

Na execução observada, foram reportadas 2 linhas como entrada da query.

Como o filtro:

```python
value >= 100
```

mantinha somente:

```text
A → 100
B → 200
```

foi realizada posteriormente uma query de controle para investigar se o valor `2` estava relacionado ao filtro.

#### `stateOperators = []`

Nenhum operador stateful foi identificado.

Isso é coerente com a transformação:

```python
filter()
```

porque cada linha pode ser analisada independentemente, sem necessidade de manter informações de micro-batches anteriores.

# Experimento A2 - Operação Stateful

## Transformação

```python
df_stream_stateful = (
    spark.readStream
    .format("delta")
    .table(sourceA)
)

df_agg = (
    df_stream_stateful
    .groupBy("customer_id")
    .agg(
        F.sum("value").alias("total_value")
    )
)
```

A operação:

```python
groupBy("customer_id")
```

seguida de:

```python
sum("value")
```

exige que o Spark mantenha uma agregação acumulada por cliente.

---

## Action

```python
query_stateful = (
    df_agg.writeStream
    .format("delta")
    .outputMode("complete")
    .option("checkpointLocation", checkpoint_stateful)
    .trigger(availableNow=True)
    .toTable(target_stateful)
)

query_stateful.awaitTermination()
```

### Resultado

```text
A → 150
B → 200
C → 80
```

O valor de `A` ficou igual a `150` porque:

```text
100 + 50 = 150
```

---

## Métricas observadas - Stateful

```python
for p in query_stateful.recentProgress:
    print("batchId:", p.batchId)
    print("inputRows:", p.numInputRows)

    for s in p.stateOperators:
        print("operatorName:", s.operatorName)
        print("numRowsTotal:", s.numRowsTotal)
        print("numRowsUpdated:", s.numRowsUpdated)
        print("memoryUsedBytes:", s.memoryUsedBytes)
```

Saída observada:

```text
batchId = 0
numInputRows = 4
operatorName = stateStoreSave
numRowsTotal = 3
numRowsUpdated = 3
memoryUsedBytes ≈ 265 MB
```

---

## Interpretação das métricas

### `numInputRows = 4`

Quatro registros da fonte participaram do processamento:

```text
A → 100
A → 50
B → 200
C → 80
```

### `operatorName = stateStoreSave`

Indica a presença de um operador associado à gravação/manutenção do estado.

Isso diferencia claramente este caso da query stateless, na qual:

```text
stateOperators = []
```

### `numRowsTotal = 3`

Ao final do processamento, o state mantinha três entradas:

```text
A → 150
B → 200
C → 80
```

Portanto:

```text
3 customer_id distintos
→ 3 entradas no state
```

### `numRowsUpdated = 3`

As três chaves existentes no resultado tiveram state criado ou atualizado:

```text
A
B
C
```

Por isso o valor observado foi `3`.

### `memoryUsedBytes`

Representa a memória utilizada pelo State Store.

O valor observado foi muito maior do que o tamanho lógico das três linhas.

Portanto:

> `memoryUsedBytes` não deve ser interpretado como o tamanho bruto de `A`, `B` e `C`.

A métrica também envolve estruturas internas e overhead do State Store.

# Experimento B - Evolução do State

## Objetivo

Demonstrar que uma query stateful consegue utilizar informação mantida de micro-batches anteriores para atualizar incrementalmente uma agregação.

---

## Setup

```python
sourceB = "workspace.default.lab29_source_b"
targetB = "workspace.default.lab29_stateful_b"

checkpointB = "/Volumes/workspace/default/lab29_volume/checkpoint_b"

spark.sql(f"DROP TABLE IF EXISTS {sourceB}")
spark.sql(f"DROP TABLE IF EXISTS {targetB}")

dbutils.fs.rm(checkpointB, True)
```

---

## Primeiro lote

```python
batch1 = [
    ("A", 100.0),
    ("B", 50.0)
]

df_batch1 = spark.createDataFrame(
    batch1,
    ["customer_id", "value"]
)

df_batch1.write \
    .format("delta") \
    .mode("overwrite") \
    .saveAsTable(sourceB)
```

---

## Query Stateful

```python
df_stream_b = (
    spark.readStream
    .format("delta")
    .table(sourceB)
)

df_state_b = (
    df_stream_b
    .groupBy("customer_id")
    .agg(
        F.sum("value").alias("total_value")
    )
)
```

---

## Primeira execução

```python
query_b1 = (
    df_state_b.writeStream
    .format("delta")
    .outputMode("complete")
    .option("checkpointLocation", checkpointB)
    .trigger(availableNow=True)
    .toTable(targetB)
)

query_b1.awaitTermination()
```

### Resultado

```text
A → 100
B → 50
```

Conceitualmente, o state passou a conter:

```text
A → 100
B → 50
```

---

## Segundo lote

```python
batch2 = [
    ("A", 30.0),
    ("C", 70.0)
]

df_batch2 = spark.createDataFrame(
    batch2,
    ["customer_id", "value"]
)

df_batch2.write \
    .format("delta") \
    .mode("append") \
    .saveAsTable(sourceB)
```

---

## Segunda execução

Foi utilizado o mesmo checkpoint:

```python
query_b2 = (
    df_state_b.writeStream
    .format("delta")
    .outputMode("complete")
    .option("checkpointLocation", checkpointB)
    .trigger(availableNow=True)
    .toTable(targetB)
)

query_b2.awaitTermination()
```

### Resultado

```text
A → 130
B → 50
C → 70
```

---

## Interpretação

O segundo lote continha apenas:

```text
A → 30
C → 70
```

Mesmo assim, o resultado final foi:

```text
A → 130
B → 50
C → 70
```

O valor anterior:

```text
A → 100
```

não veio do segundo micro-batch.

Ele foi recuperado do estado construído anteriormente.

Assim:

```text
A anterior = 100
A novo     = 30

100 + 30 = 130
```

O cliente `B` também permaneceu:

```text
B → 50
```

mesmo sem aparecer no segundo lote.

---

## Importância do checkpoint

As duas execuções utilizaram:

```python
checkpointB
```

Isso significa que ambas pertenciam à continuidade da mesma query stateful.

Conceitualmente:

```text
query_b1
→ cria state

checkpointB
→ persiste informações necessárias à recuperação

query_b2
→ reutiliza checkpointB
→ recupera state anterior
→ atualiza state
```

Se fosse iniciado um novo checkpoint, o processamento começaria como uma nova execução, sem o histórico daquele state anterior.

```python
progress = query_b2.recentProgress

for p in progress:
```

```text
numRowsTotal = 3

numShufflePartitions = 200
numStateStoreInstances = 200
```

---

# Interpretação detalhada

## `batchId = 1`

Representa o segundo micro-batch da query.

O batch anterior foi:

```text
batchId = 0
```

e construiu o estado inicial.

---

## `numInputRows = 2`

No segundo lote entraram:

```text
A → 30
C → 70
```

Portanto duas linhas foram processadas.

---

## `numRowsTotal = 3`

Após o segundo micro-batch, o state continha:

```text
A → 130
B → 50
C → 70
```

Logo:

```text
3 chaves
→ numRowsTotal = 3
```

---

## `numRowsUpdated = 2`

Duas entradas do state foram alteradas neste micro-batch:

```text
A
C
```

### Cliente A

Já existia:

```text
A → 100
```

e foi atualizado para:

```text
A → 130
```

### Cliente C

Não existia anteriormente.

Foi criado:

```text
C → 70
```

Portanto, também contou como entrada atualizada/criada no state.

### Cliente B

Permaneceu:

```text
B → 50
```

mas não recebeu novos dados.

Por isso:

```text
numRowsUpdated = 2
```

e não `3`.

---

## `numRowsRemoved = 0`

Nenhuma chave foi removida do state.

A query utilizada era:

```python
groupBy("customer_id").sum("value")
```

e não possuía:

```python
withWatermark(...)
```

nem agregação temporal com:

```python
window(...)
```

Portanto, não havia naquele experimento um critério temporal utilizado para expirar aquelas entradas de state.

---

## `memoryUsedBytes`

Foi observado aproximadamente:

```text
26.7 MB
```

de memória reportada pelo State Store.

Esse valor não representa apenas o tamanho lógico das três linhas:

```text
A
B
C
```

Também existe overhead relacionado às estruturas internas utilizadas para manter o estado.

---

## `numRowsDroppedByWatermark = 0`

Nenhum registro foi descartado por estar atrasado em relação a um watermark.

Isso é esperado porque o Experimento B não utilizava watermark.

---

## `numShufflePartitions = 200`

O operador stateful utilizou:

```text
200 partições de shuffle
```

na execução observada.

A agregação:

```python
groupBy("customer_id")
```

precisa garantir que registros da mesma chave sejam processados de forma compatível com a agregação.

Conceitualmente:

```text
groupBy
   ↓
Shuffle
   ↓
particionamento por chave
   ↓
operação stateful
```

---

## `numStateStoreInstances = 200`

Foram reportadas:

```text
200 instâncias de State Store
```

no operador.

Neste experimento:

```text
numShufflePartitions = 200
numStateStoreInstances = 200
```

Isso mostrou uma relação direta entre o particionamento do operador stateful e as instâncias utilizadas para manter o state.

### Importante

Não deve ser concluído que:

```text
Stateful Processing sempre usa 200 partições
```

Esse foi o valor observado nesta execução e neste ambiente.

# Experimento D - Watermark e remoção de State antigo

## Objetivo

Demonstrar como watermark e agregação por janela podem permitir a remoção de state antigo.

Também foi analisada a diferença entre:

```text
outputMode("complete")
```

e:

```text
outputMode("append")
```

---

# Dados iniciais

```python
from datetime import datetime

sourceD = "workspace.default.lab29_source_d"
targetD = "workspace.default.lab29_stateful_d"

checkpointD = "/Volumes/workspace/default/lab29_volume/checkpoint_d"

spark.sql(f"DROP TABLE IF EXISTS {sourceD}")
spark.sql(f"DROP TABLE IF EXISTS {targetD}")

dbutils.fs.rm(checkpointD, True)
```

O retorno:

```text
True
```

do `dbutils.fs.rm()` indicou que havia conteúdo anterior no checkpoint e ele foi removido com sucesso.

---

## Primeiro lote

```python
data_d1 = [
    ("A", 100.0, datetime(2026, 9, 23, 10, 1, 0)),
    ("A", 50.0,  datetime(2026, 9, 23, 10, 3, 0)),
    ("B", 80.0,  datetime(2026, 9, 23, 10, 7, 0))
]

df_d1 = spark.createDataFrame(
    data_d1,
    ["customer_id", "value", "event_time"]
)

df_d1.write \
    .format("delta") \
    .mode("overwrite") \
    .saveAsTable(sourceD)
```

---

# Agregação com Watermark

```python
df_stream_d = (
    spark.readStream
    .format("delta")
    .table(sourceD)
)

df_windowed = (
    df_stream_d
    .withWatermark(
        "event_time",
        "10 minutes"
    )
    .groupBy(
        F.window(
            F.col("event_time"),
            "5 minutes"
        ),
        F.col("customer_id")
    )
    .agg(
        F.sum("value").alias("total_value")
    )
)
```

O nome `df_windowed` é apenas uma variável Python escolhida para representar um DataFrame que recebeu uma agregação por janela.

---

# Primeira tentativa - `complete`

Inicialmente foi utilizada:

```python
.outputMode("complete")
```

### Resultado

As janelas foram exibidas imediatamente:

```text
10:00–10:05 | A | 150
10:05–10:10 | B | 80
```

Entretanto, mesmo com o avanço do watermark:

```text
numRowsRemoved = 0
```

O experimento mostrou que:

```text
watermark presente
≠
remoção automática de state em qualquer output mode
```

No modo `complete`, o state da agregação é mantido para permitir que toda a tabela agregada continue sendo emitida.

Por isso o experimento foi reiniciado utilizando `append`.

---

```python
query_d1 = (

```

```text
10:30–10:35 | C → 200
```

Portanto:

```text
3 entradas
→ numRowsTotal = 3
```

---

## Por que `numRowsUpdated = 1`?

Somente a nova janela associada a `C` foi criada/atualizada naquele micro-batch.

Logo:

```text
numRowsUpdated = 1
```

---

## Por que `numRowsRemoved = 0`?

Apesar da entrada às `10:30`, o watermark utilizado naquele trigger ainda era:

```text
09:57
```

Portanto nenhuma das janelas antigas ainda estava expirada naquele batch.

---

## Por que `numRowsDroppedByWatermark = 0`?

Nenhum registro de entrada chegou atrasado em relação ao watermark.

O experimento estava testando remoção de state antigo, e não late data.

---

# Batch 3 - avanço do watermark e remoção do State

Foi observado:

```text
batchId = 3
numInputRows = 0

watermark = 10:20

numRowsTotal = 1
numRowsUpdated = 0
numRowsRemoved = 2
numRowsDroppedByWatermark = 0
```

Este foi o resultado mais importante do Experimento D.

---

## Por que o watermark avançou para `10:20`?

O maior `event_time` observado anteriormente passou a ser:

```text
10:30
```

Com atraso configurado de:

```text
10 minutos
```

temos:

```text
10:30 - 10 minutos = 10:20
```

---

## Por que `numRowsRemoved = 2`?

As duas janelas antigas terminavam em:

```text
A → 10:05
B → 10:10
```

O watermark agora era:

```text
10:20
```

Portanto ambas ficaram definitivamente atrás do watermark.

Conceitualmente:

```text
A → removido do State Store
B → removido do State Store
```

Logo:

```text
numRowsRemoved = 2
```

---

## Por que `numRowsTotal = 1`?

Antes da remoção havia:

```text
A
B
C
```

três entradas no state.

Foram removidas:

```text
A
B
```

restando apenas:

```text
C → janela 10:30–10:35
```

Portanto:

```text
3 - 2 = 1
```

e:

```text
numRowsTotal = 1
```

---

## Por que `numRowsUpdated = 0`?

Esse batch não recebeu novos dados:

```text
numInputRows = 0
```

O trabalho realizado foi principalmente avanço do watermark e limpeza de state antigo.

Por isso:

```text
numRowsUpdated = 0
```

---

## `numRowsRemoved` vs `numRowsDroppedByWatermark`

Essa diferença é importante.

### `numRowsRemoved = 2`

Significa:

```text
duas entradas antigas foram removidas do State Store
```

### `numRowsDroppedByWatermark = 0`

Significa:

```text
nenhum registro novo de entrada foi descartado por chegar tarde demais
```

Portanto:

```text
remoção de state antigo
≠
descarte de late data
```

---

# Complete vs Append

O Experimento D permitiu observar uma diferença importante.

## `complete`

```text
watermark existe
↓
agregação completa é emitida
↓
state permanece mantido
↓
numRowsRemoved = 0
```

## `append`

```text
watermark avança
↓
janelas ficam definitivamente finalizadas
↓
state antigo pode ser removido
↓
numRowsRemoved = 2
```

Assim, o experimento mostrou que:

> Watermark sozinho não deve ser analisado isoladamente. O comportamento do state também depende da operação e do output mode utilizado.

# Aplicação prática em produção

Stateful Processing não é uma funcionalidade que o engenheiro escolhe de forma isolada.

A própria lógica da query pode exigir state.

Exemplos de operações tipicamente stateful:

```text
GROUP BY + SUM
GROUP BY + COUNT
AVG
DISTINCT
dropDuplicates
window aggregation
stream-stream join
```

Exemplos tipicamente stateless:

```text
SELECT
WHERE
CAST
CASE WHEN
transformações por linha
stream-static join
```

A preocupação prática passa a ser:

```text
A query é stateful?
        ↓
Quanto state existe?
        ↓
Esse state está crescendo?
        ↓
Ele pode ser removido?
        ↓
Existe watermark quando aplicável?
        ↓
A duração dos micro-batches está aumentando?
        ↓
A memória do State Store está crescendo?
```

Métricas importantes para acompanhamento:

```text
numRowsTotal
numRowsUpdated
numRowsRemoved
memoryUsedBytes
numRowsDroppedByWatermark
numShufflePartitions
numStateStoreInstances
```

---

# Relação com arquitetura Bronze / Silver / Gold

Stateful e stateless não devem ser utilizados para definir diretamente a camada arquitetural.

Não deve ser assumido:

```text
Silver = stateless
Gold = stateful
```

A camada deve ser definida pela responsabilidade dos dados.

Exemplos:

### Silver

Pode conter operações stateful quando forem necessárias para:

```text
deduplicação
integração
tratamento de late data
stream-stream joins
qualidade
```

### Gold

É um local natural para:

```text
agregações
KPIs
métricas
rankings
modelagem analítica
```

Portanto, a regra prática é:

> Primeiro define-se a necessidade da regra de negócio. Depois avalia-se o custo e o comportamento que essa operação impõe ao Spark.

# Conclusão

O Lab 29 demonstrou que Stateful Processing ocorre quando o Spark precisa manter informações entre micro-batches para continuar corretamente uma operação incremental.

No Experimento A foi possível diferenciar claramente:

```text
Stateless
→ stateOperators = []

Stateful
→ stateStoreSave
```

No Experimento B foi demonstrado que o state anterior influencia batches futuros:

```text
A = 100
+
A = 30
=
A = 130
```

O uso do mesmo checkpoint permitiu continuar a mesma query stateful e recuperar o state construído anteriormente.

No Experimento C foram observadas métricas internas do State Store:

```text
numRowsTotal = 3
numRowsUpdated = 2
numRowsRemoved = 0
numShufflePartitions = 200
numStateStoreInstances = 200
```

Essas métricas permitiram relacionar diretamente o conteúdo lógico do state com a execução física da query.

No Experimento D foi demonstrado o relacionamento entre:

```text
Watermark
+
Window
+
Output Mode
+
State
```

Na primeira tentativa com `complete`, o state não foi removido.

Na segunda tentativa com `append`, o watermark avançou até:

```text
10:20
```

e as janelas antigas:

```text
10:00–10:05
10:05–10:10
```

foram removidas do State Store.

A evidência final foi:

```text
numRowsTotal = 1
numRowsRemoved = 2
```

O laboratório mostrou que Stateful Processing adiciona uma nova dimensão de observabilidade ao Structured Streaming.

Além de analisar:

```text
shuffle
partições
skew
joins
broadcast
```

em workloads stateful também passa a ser importante analisar:

```text
tamanho do state
crescimento do state
memória utilizada
linhas atualizadas
linhas removidas
watermark
checkpoint
duração dos micro-batches
```

Assim, o principal aprendizado do Lab 29 é:

> Uma operação stateful não deve ser evitada quando é necessária para atender à regra de negócio. O papel do engenheiro é reconhecer quando existe state, entender quanto estado está sendo mantido, observar seu comportamento ao longo dos micro-batches e garantir que esse state não se torne um gargalo de processamento.
