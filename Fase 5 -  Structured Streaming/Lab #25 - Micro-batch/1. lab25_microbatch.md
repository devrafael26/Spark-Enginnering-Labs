## Spark Engineering Lab 25 - Micro-batch

## Categoria

Structured Streaming

## Objetivo

Entender como o Apache Spark Structured Streaming processa dados de forma incremental por meio de micro-batches e observar, na prática, como uma única execução de streaming pode ser dividida em múltiplos batches.

O laboratório também buscou diferenciar:

- lote lógico criado no código;
- arquivo físico armazenado em uma tabela Delta;
- micro-batch processado pelo Structured Streaming;
- checkpoint da streaming query;
- controle de entrada com `maxFilesPerTrigger`.

---

## Pergunta

Como o Structured Streaming divide e processa os dados disponíveis em micro-batches?

Perguntas auxiliares:

- O que caracteriza um micro-batch?
- Como uma tabela Delta pode ser usada como source de streaming?
- Como provocar mais de um micro-batch em um ambiente Databricks Serverless?
- Como observar os `batchId` e as métricas de cada micro-batch?
- Qual é a diferença entre arquivos físicos da source e micro-batches?

---

## Conceito

Um **micro-batch** é uma unidade incremental de processamento do Structured Streaming.

A ideia conceitual é:

```text
Source
  ↓
novos dados disponíveis
  ↓
Micro-batch 0
  ↓
processamento
  ↓
commit

novos dados ainda disponíveis
  ↓
Micro-batch 1
  ↓
processamento
  ↓
commit
```

O micro-batch não deve ser confundido com um arquivo temporário.

Ele representa uma parcela dos dados disponíveis que será processada em uma execução incremental da streaming query.

Em uma source Kafka, essa parcela pode ser definida a partir dos offsets disponíveis.

Em uma source baseada em arquivos ou Delta, a entrada também pode ser limitada por quantidade ou volume de arquivos.

---

## Ambiente

Databricks Serverless.

No ambiente utilizado neste laboratório, foi adotado:

```python
.trigger(availableNow=True)
```

A documentação da Databricks recomenda `Trigger.AvailableNow()` para streaming incremental em Serverless e permite ajustar o tamanho dos batches com opções como `maxFilesPerTrigger` e `maxBytesPerTrigger`.

Documentação oficial:

https://docs.databricks.com/gcp/en/compute/serverless/streaming

# Experimento A - Criar e consumir uma source Delta como streaming

## Objetivo do experimento

Criar uma tabela Delta comum e depois consumi-la através da API `readStream`, demonstrando a diferença entre:

```text
tabela Delta
```

e:

```text
Streaming DataFrame que lê essa tabela
```

O experimento A serviu principalmente como preparação para os experimentos seguintes.

Ele demonstrou o mecanismo básico de:

```text
Delta source
   ↓
readStream
   ↓
Streaming DataFrame
   ↓
writeStream
   ↓
Delta target
```

---

## Dados

Foram criados 1.000 registros artificiais com `spark.range()`.

---

Foi criado um Volume específico para o laboratório:

```sql

```

Estrutura utilizada:

```text

    checkpoints/
```

## Configuração

```python
from pyspark.sql import functions as F

catalog = "workspace"
schema = "default"

source_table = f"{catalog}.{schema}.lab25_source"
target_table = f"{catalog}.{schema}.lab25_target"

checkpoint_path = (
    "/Volumes/workspace/default/lab25_volume/checkpoints/exp_a"
)
```

---

## Limpeza do estado anterior

```python
spark.sql(f"DROP TABLE IF EXISTS {source_table}")
spark.sql(f"DROP TABLE IF EXISTS {target_table}")
```

O `DROP TABLE IF EXISTS` foi utilizado para tornar o laboratório reproduzível.

Na primeira execução, caso as tabelas não existam, o comando não altera nada.

Em uma nova execução completa do laboratório, ele remove as tabelas anteriores para recriar o cenário.

---

## Criação da tabela Delta de origem

```python
df_source = (
    spark.range(0, 1000)
    .withColumn("valor", F.col("id") * 10)
    .withColumn("created_at", F.current_timestamp())
)

(
    df_source.write
    .format("delta")
    .mode("overwrite")
    .saveAsTable(source_table)
)
```

Aqui:

```text
df_source
```

é um DataFrame batch comum.

Ele foi utilizado para criar a tabela Delta:

```text
workspace.default.lab25_source
```

---

## Transformação da leitura em streaming

```python
df_stream = (
    spark.readStream
    .format("delta")
    .table(source_table)
)

print("É streaming?", df_stream.isStreaming)
```

Resultado esperado:

```text
É streaming? True
```

Importante:

`readStream` não transforma fisicamente a tabela Delta em outro tipo de tabela.

A tabela continua sendo Delta.

O que muda é a forma como ela é consumida:

```text
Delta Table
   ├── spark.read       → Batch DataFrame
   └── spark.readStream → Streaming DataFrame
```

---

## Action / Execução

```python
query_a = (
    df_stream
    .writeStream
    .format("delta")
    .outputMode("append")
    .option("checkpointLocation", checkpoint_path)
    .trigger(availableNow=True)
    .toTable(target_table)
)

query_a.awaitTermination()
```

`query_a` é um objeto `StreamingQuery`.

Ele representa a execução da streaming query e permite operações como:

```python
query_a.awaitTermination()
query_a.status
query_a.recentProgress
```

O `awaitTermination()` aguarda o término da execução.

Como o trigger utilizado foi `AvailableNow`, a query processa os dados disponíveis e encerra.

---

## Validação

```python
spark.table(target_table).count()
```

Resultado observado:

```text
1000
```

# Experimento B - Provocar múltiplos micro-batches

## Objetivo do experimento

Criar uma source Delta com vários arquivos físicos e limitar a leitura do Structured Streaming para:

```text
máximo de 1 arquivo por micro-batch
```

permitindo observar múltiplos batches dentro de uma única execução com `AvailableNow`.

---

## Configuração

```python
source_b = f"{catalog}.{schema}.lab25_source_b"
target_b = f"{catalog}.{schema}.lab25_target_b"

checkpoint_b = (
    "/Volumes/workspace/default/lab25_volume/checkpoints/exp_b"
)

spark.sql(f"DROP TABLE IF EXISTS {source_b}")
spark.sql(f"DROP TABLE IF EXISTS {target_b}")
```

---

## Criação dos dados

Foram realizadas cinco gravações lógicas independentes.

Cada gravação continha 1.000 registros.

```python
for lote in range(5):

    df_lote = (
        spark.range(lote * 1000, (lote + 1) * 1000)
        .withColumn("lote_origem", F.lit(lote))
    )

    (
        df_lote.write
        .format("delta")
        .mode("append")
        .saveAsTable(source_b)
    )
```

Resultado lógico:

```text
Lote 0 → 1000 linhas
Lote 1 → 1000 linhas
Lote 2 → 1000 linhas
Lote 3 → 1000 linhas
Lote 4 → 1000 linhas

Total = 5000 linhas
```

Importante:

```text
gravação lógica
≠
arquivo físico
```

Cinco gravações lógicas não significam necessariamente cinco arquivos físicos.

---

## Leitura streaming com limite de arquivos por micro-batch

```python
df_stream_b = (
    spark.readStream
    .format("delta")
    .option("maxFilesPerTrigger", 1)
    .table(source_b)
)
```

A configuração:

```python
.option("maxFilesPerTrigger", 1)
```

significa:

```text
processar no máximo 1 novo arquivo da source por micro-batch
```

Ela controla a entrada do micro-batch.

Ela não cria arquivos e não controla a quantidade de arquivos gravados no target.

Documentação oficial:

https://docs.databricks.com/aws/en/structured-streaming/delta-lake

---

## Execução

```python
query_b = (
    df_stream_b
    .writeStream
    .format("delta")
    .outputMode("append")
    .option("checkpointLocation", checkpoint_b)
    .trigger(availableNow=True)
    .toTable(target_b)
)

query_b.awaitTermination()
```

---

## Validação

```python
spark.table(target_b).count()
```

Resultado observado:

```text
5000
```

Isso demonstrou que todos os registros disponíveis foram processados.

O `AvailableNow` não significa necessariamente um único micro-batch.

Ele pode executar múltiplos micro-batches até consumir todos os dados disponíveis.

```python
display(arquivos_source_b)
```

# O que está documentado oficialmente

## Trigger.AvailableNow

No Databricks Serverless, `Trigger.AvailableNow()` é utilizado para processamento incremental dos dados disponíveis.

A execução processa os dados disponíveis desde o último checkpoint e termina.

Documentação:

https://docs.databricks.com/gcp/en/compute/serverless/streaming

## maxFilesPerTrigger

`maxFilesPerTrigger` limita a quantidade máxima de novos arquivos considerados por micro-batch em sources compatíveis.

No laboratório:

Documentação:

https://docs.databricks.com/aws/en/structured-streaming/delta-lake

## Checkpoint

O checkpoint mantém o progresso da streaming query.

Durante o laboratório foi observado que:

- reutilizar o mesmo checkpoint com a mesma source permite continuidade;
- apagar e recriar a source Delta e depois tentar reutilizar o checkpoint antigo pode gerar incompatibilidade;
- para reiniciar completamente um laboratório, source, target e checkpoint precisam ser tratados como parte do mesmo estado experimental.

Esse conceito será aprofundado no Lab 26 - Checkpoint.

# Relação com Kafka

Neste laboratório foi utilizada uma tabela Delta como source para tornar o comportamento observável.

A mesma ideia conceitual se aplica a outras fontes.

Com Delta/file source:

```text
maxFilesPerTrigger
```

controla quantos arquivos podem ser processados em cada micro-batch.

Com Kafka:

```text
maxOffsetsPerTrigger
```

pode limitar a quantidade de offsets processados por trigger.

A unidade de controle muda conforme a natureza da source.

# Conclusão

O Lab 25 demonstrou que o Structured Streaming pode processar uma fonte de dados através de múltiplas execuções incrementais chamadas **micro-batches**.

No experimento principal, foram realizadas cinco gravações lógicas totalizando 5.000 registros em uma tabela Delta.

O estado físico observado da source continha nove arquivos.

Ao configurar:

```python
.option("maxFilesPerTrigger", 1)
```

e executar a streaming query com:

```python
.trigger(availableNow=True)
```

o Structured Streaming processou os nove arquivos em nove micro-batches.

Os progressos observados foram:

```text
8 micro-batches × 125 linhas
+
1 micro-batch × 4000 linhas
=
5000 linhas
```

O total correspondeu exatamente aos 5.000 registros gravados no target.

A principal conclusão do laboratório é:

> **Micro-batch é uma unidade incremental de processamento do Structured Streaming. A quantidade de dados processada em cada micro-batch pode ser controlada de acordo com a fonte. No experimento, limitamos a entrada a um arquivo por micro-batch e conseguimos observar nove micro-batches consumindo nove arquivos físicos até processar todas as 5.000 linhas disponíveis.**

O laboratório também consolidou uma distinção importante:

```text
lote lógico
≠
arquivo físico
≠
micro-batch
```

Essa separação será fundamental para os próximos laboratórios de Structured Streaming.
