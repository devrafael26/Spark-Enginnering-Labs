## Spark Engineering Lab 26 - Checkpoint

## Categoria

Structured Streaming

## Objetivo

Entender como o checkpoint registra o progresso de uma consulta Structured Streaming e como esse histórico permite que uma nova execução retome o processamento a partir do ponto já registrado anteriormente.

O laboratório também busca diferenciar claramente:

- os dados da **source**;
- o histórico de progresso mantido no **checkpoint**;
- a tabela de destino (**sink**);
- a identidade lógica da streaming query (`query.id`);
- a identidade de cada execução individual (`runId`).

---

## Pergunta

**Como o checkpoint permite que uma consulta Structured Streaming reiniciada continue o processamento a partir do progresso anteriormente registrado?**

---

## Conceito principal

No Structured Streaming, o checkpoint não armazena os dados da source.

Ele armazena informações necessárias para acompanhar e recuperar o progresso da streaming query.

De forma simplificada:

```text
SOURCE
  ↓
micro-batch
  ↓
processamento
  ↓
SINK

ao mesmo tempo:

CHECKPOINT
  ↓
progresso da query
offsets
commits
metadata
```

Quando uma nova execução utiliza o mesmo checkpoint, o Spark consegue recuperar o progresso registrado anteriormente.

Quando uma nova localização de checkpoint é utilizada, a nova query não possui aquele histórico anterior.

---

## Estrutura utilizada no laboratório

```python
CATALOG = "workspace"
SCHEMA = "default"

VOLUME = "lab26_checkpoint"

INPUT_PATH = f"/Volumes/{CATALOG}/{SCHEMA}/{VOLUME}/input"
CHECKPOINT_PATH = f"/Volumes/{CATALOG}/{SCHEMA}/{VOLUME}/checkpoint"
CHECKPOINT_NEW_PATH = f"/Volumes/{CATALOG}/{SCHEMA}/{VOLUME}/checkpoint_new"

TARGET_TABLE = f"{CATALOG}.{SCHEMA}.lab26_checkpoint_result"
TARGET_TABLE_NEW = f"{CATALOG}.{SCHEMA}.lab26_checkpoint_result_new"
```

Volume criado:

```sql
CREATE VOLUME IF NOT EXISTS workspace.default.lab26_checkpoint;
```

Estrutura conceitual:

```text
workspace
└── default
    ├── Volume: lab26_checkpoint
    │   ├── input/
    │   ├── checkpoint/
    │   └── checkpoint_new/
    │
    ├── Tabela: lab26_checkpoint_result
    └── Tabela: lab26_checkpoint_result_new
```

### Distinção importante

`INPUT_PATH`, `CHECKPOINT_PATH` e `CHECKPOINT_NEW_PATH` são caminhos dentro de um Unity Catalog Volume.

As variáveis:

```text
workspace.default.lab26_checkpoint_result
workspace.default.lab26_checkpoint_result_new
```

representam tabelas Delta registradas no Unity Catalog.

Elas não representam arquivos Parquet individuais.

# Experimento A - Primeira execução com checkpoint

## Objetivo

Criar a source inicial, iniciar uma streaming query com checkpoint novo e verificar a primeira carga gravada na tabela Delta.

---

## Dados

Foram criados 30 registros:

```python
from pyspark.sql import functions as F

df_inicial = (
    spark.range(1, 31)
    .withColumn("grupo", F.lit("carga_inicial"))
)

display(df_inicial)
```

Resultado:

```text
IDs: 1 até 30
Total: 30 registros
```

O `spark.range(1, 31)` utiliza limite final exclusivo.

---

## Escrita da source

```python
(
    df_inicial
    .repartition(3)
    .write
    .mode("overwrite")
    .parquet(INPUT_PATH)
)
```

No experimento, `repartition(3)` produziu três partições para essa escrita e foram observados três arquivos de dados Parquet no diretório da source.

Verificação:

```python
display(dbutils.fs.ls(INPUT_PATH))
```

### Observação

O DataFrame já estava definido antes da escrita, porém ainda não estava persistido como aqueles arquivos Parquet.

A gravação física aconteceu no `.write.parquet(INPUT_PATH)`.

No experimento foi observado:

```text
DataFrame
30 registros
    ↓
repartition(3)
    ↓
3 partições para a escrita
    ↓
3 arquivos Parquet observados
```

Esse resultado pertence ao experimento e não deve ser generalizado como regra universal de que qualquer `repartition(N)` produzirá exatamente `N` arquivos em qualquer cenário de escrita.

---

## Transformações

Foi criada uma coluna constante:

```python
.withColumn("grupo", F.lit("carga_inicial"))
```

E os dados foram redistribuídos para três partições antes da escrita:

```python
.repartition(3)
```

---

## Leitura streaming

```python
stream_df = (
    spark.readStream
    .schema(df_inicial.schema)
    .format("parquet")
    .load(INPUT_PATH)
)
```

### Interpretação

Os arquivos Parquet não foram "transformados em arquivos de streaming".

Foi criado um **Streaming DataFrame cuja source é o diretório de arquivos Parquet**.

A configuração:

```python
.schema(df_inicial.schema)
```

informa explicitamente o schema esperado para os arquivos da source.

Ela não possui relação com o progresso do checkpoint.

Separação:

```text
.schema(...)
    ↓
estrutura dos dados

.load(INPUT_PATH)
    ↓
localização da source

checkpointLocation
    ↓
progresso da streaming query
```

---

## Action

```python
query = (
    stream_df.writeStream
    .format("delta")
    .option("checkpointLocation", CHECKPOINT_PATH)
    .trigger(availableNow=True)
    .toTable(TARGET_TABLE)
)

query.awaitTermination()
```

Essa etapa iniciou de fato a streaming query.

Fluxo:

```text
arquivos Parquet
      ↓
readStream
      ↓
Streaming DataFrame
      ↓
writeStream
      ↓
AvailableNow
      ↓
processamento
      ↓
tabela Delta
      ↓
checkpoint
```

---

## Comando de análise

```python
spark.sql(f"""
SELECT *
FROM {TARGET_TABLE}
ORDER BY id
""").show(50, truncate=False)
```

```python
spark.sql(f"""
SELECT COUNT(*) AS total_registros
FROM {TARGET_TABLE}
""").show()
```

---

## Resultado observado

```text
30 registros
```

Como o checkpoint era novo, não existia progresso anterior registrado para essa query.

Os 30 registros disponíveis na source foram processados e gravados na tabela Delta.

# Experimento B - Inspeção do checkpoint

## Objetivo

Inspecionar a estrutura persistida pelo Structured Streaming após a execução do Experimento A.

---

## Comando de análise

```python
display(dbutils.fs.ls(CHECKPOINT_PATH))
```

---

## Resultado observado

Foram encontrados:

```text
sources/
offsets/
metadata
commits/
```

No nível principal do diretório, os diretórios apareceram com `size = 0`, enquanto o arquivo `metadata` apresentou tamanho próprio.

Isso não significa que `offsets`, `commits` ou `sources` estavam vazios.

Eles são diretórios.

---

## Inspeção de offsets

```python
display(dbutils.fs.ls(f"{CHECKPOINT_PATH}/offsets"))
```

Foi observado:

```text
name = 0
size ≈ 2112 bytes
```

---

## Inspeção de commits

```python
display(dbutils.fs.ls(f"{CHECKPOINT_PATH}/commits"))
```

Foi observado:

```text
name = 0
size ≈ 29 bytes
```

---

## Inspeção do metadata

```python
dbutils.fs.head(f"{CHECKPOINT_PATH}/metadata")
```

Foi retornado um UUID no formato:

```text
xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx
```

---

## Interpretação

Os arquivos de nome `0` observados em:

```text
offsets/0
commits/0
```

estão associados ao primeiro micro-batch observado na execução.

Conexão com o Lab 25:

```text
Lab 25
Micro-batch 0
     ↓
processamento

Lab 26
Micro-batch 0
     ↓
offsets/0
commits/0
```

O `metadata` contém a identidade única da streaming query.

O `modificationTime` exibido por `dbutils.fs.ls()` corresponde ao timestamp de modificação do item no armazenamento e não representa um offset do streaming.

# Experimento C - Novos dados utilizando o mesmo checkpoint

## Objetivo

Adicionar novos dados à mesma source e reiniciar a streaming query utilizando o mesmo checkpoint para verificar a continuidade do processamento.

---

## Nova carga

```python
df_novo = (
    spark.range(31, 51)
    .withColumn("grupo", F.lit("segunda_carga"))
)

display(df_novo)
```

Resultado:

```text
IDs: 31 até 50
Total: 20 registros
```

---

## Adição de novos arquivos

```python
(
    df_novo
    .repartition(2)
    .write
    .mode("append")
    .parquet(INPUT_PATH)
)
```

A source passou a possuir:

```text
30 registros antigos
+
20 registros novos
=
50 registros
```

Verificação:

```python
spark.read.parquet(INPUT_PATH).count()
```

Resultado:

```text
50
```

---

## Nova definição da leitura streaming

```python
stream_df_2 = (
    spark.readStream
    .schema(df_inicial.schema)
    .format("parquet")
    .load(INPUT_PATH)
)
```

### Distinção importante

Criar `stream_df_2` não apaga o checkpoint e não faz a query esquecer o progresso anterior.

Esse objeto apenas define novamente uma leitura streaming para a mesma source.

Quem liga a nova execução ao histórico anterior é:

```python
.option("checkpointLocation", CHECKPOINT_PATH)
```

---

## Nova execução com o mesmo checkpoint

```python
query_2 = (
    stream_df_2.writeStream
    .format("delta")
    .option("checkpointLocation", CHECKPOINT_PATH)
    .trigger(availableNow=True)
    .toTable(TARGET_TABLE)
)

query_2.awaitTermination()
```

---

## Comando de análise

```python
spark.sql(f"""
SELECT COUNT(*) AS total_registros
FROM {TARGET_TABLE}
""").show()
```

Resultado:

```text
50
```

Também foi possível verificar as cargas:

```python
spark.sql(f"""
SELECT
    grupo,
    COUNT(*) AS registros
FROM {TARGET_TABLE}
GROUP BY grupo
ORDER BY grupo
""").show()
```

Resultado esperado/observado conceitualmente:

```text
carga_inicial     30
segunda_carga     20
```

---

## Interpretação

Antes da segunda execução:

```text
Source: 50 registros
Checkpoint: já possuía progresso da primeira execução
```

A nova execução reutilizou o checkpoint anterior.

O checkpoint não foi zerado.

Ele foi reutilizado justamente para recuperar o progresso já persistido.

# Experimento D - Novo checkpoint

## Objetivo

Executar a mesma leitura sobre os 50 registros existentes na source, porém utilizando um checkpoint novo e uma nova tabela destino.

---

## Leitura streaming

```python
stream_df_new_checkpoint = (
    spark.readStream
    .schema(df_inicial.schema)
    .format("parquet")
    .load(INPUT_PATH)
)
```

Esse objeto continua apontando para a mesma source:

```text
INPUT_PATH
→ 50 registros disponíveis
```

---

## Execução com novo checkpoint

```python
query_new_checkpoint = (
    stream_df_new_checkpoint.writeStream
    .format("delta")
    .option("checkpointLocation", CHECKPOINT_NEW_PATH)
    .trigger(availableNow=True)
    .toTable(TARGET_TABLE_NEW)
)

query_new_checkpoint.awaitTermination()
```

---

## Comando de análise

```python
spark.sql(f"""
SELECT COUNT(*) AS total_registros
FROM {TARGET_TABLE_NEW}
""").show()
```

Resultado:

```text
50
```

---

## Resultado observado

Os 50 registros foram inseridos na **nova tabela Delta**:

```text
workspace.default.lab26_checkpoint_result_new
```

Eles não vieram da tabela antiga.

A source da execução continuou sendo:

```python
.load(INPUT_PATH)
```

---

## Interpretação

O novo checkpoint não conhece o histórico registrado no checkpoint anterior.

Portanto:

```text
SOURCE
50 registros disponíveis

CHECKPOINT NOVO
0 progresso anterior daquela query

        ↓

os 50 registros disponíveis são processados
        ↓
TARGET_TABLE_NEW
50 registros
```

Comparação:

```text
Experimento C
Source:      50
Checkpoint:  antigo
Histórico:   progresso anterior existente
Target:      tabela original
```

```text
Experimento D
Source:      50
Checkpoint:  novo
Histórico:   nenhum progresso anterior
Target:      tabela nova
```

### Conclusão importante

**O checkpoint não contém os dados da source. Ele contém o progresso da streaming query.**

Como os dados antigos ainda estavam fisicamente disponíveis na source, uma nova query com checkpoint novo pôde processá-los novamente.

Em uma fonte que possua retenção limitada, dados antigos já removidos da própria fonte não seriam recriados pelo checkpoint.

# Experimento E - `query.id` vs `runId`

## Objetivo

Observar a identidade lógica da streaming query e diferenciar essa identidade da identidade de cada execução individual.

---

## Terceira carga

```python
df_terceira_carga = (
    spark.range(51, 61)
    .withColumn("grupo", F.lit("terceira_carga"))
)

(
    df_terceira_carga
    .write
    .mode("append")
    .parquet(INPUT_PATH)
)
```

A nova carga foi adicionada na mesma **source**:

```text
INPUT_PATH
```

`INPUT_PATH` não é um checkpoint.

Após essa carga, a source passou a possuir 60 registros.

---

## Nova execução utilizando o checkpoint original

```python
stream_df_3 = (
    spark.readStream
    .schema(df_inicial.schema)
    .format("parquet")
    .load(INPUT_PATH)
)
```

```python
query_3 = (
    stream_df_3.writeStream
    .format("delta")
    .option("checkpointLocation", CHECKPOINT_PATH)
    .trigger(availableNow=True)
    .toTable(TARGET_TABLE)
)

print("Query ID :", query_3.id)
print("Run ID   :", query_3.runId)

query_3.awaitTermination()
```

Verificação:

```python
spark.sql(f"""
SELECT COUNT(*) AS total
FROM {TARGET_TABLE}
""").show()
```

Resultado:

```text
60
```

---

## Quarta carga

```python
df_quarta_carga = (
    spark.range(61, 71)
    .withColumn("grupo", F.lit("quarta_carga"))
)

(
    df_quarta_carga
    .write
    .mode("append")
    .parquet(INPUT_PATH)
)
```

A source passou a possuir 70 registros.

---

## Nova execução

```python
stream_df_4 = (
    spark.readStream
    .schema(df_inicial.schema)
    .format("parquet")
    .load(INPUT_PATH)
)
```

```python
query_4 = (
    stream_df_4.writeStream
    .format("delta")
    .option("checkpointLocation", CHECKPOINT_PATH)
    .trigger(availableNow=True)
    .toTable(TARGET_TABLE)
)

print("Query ID :", query_4.id)
print("Run ID   :", query_4.runId)

query_4.awaitTermination()
```

---

## Resultado observado

Entre as duas execuções:

```text
query.id
→ permaneceu igual

runId
→ mudou
```

---

## Interpretação

`query.id` representa a identidade lógica da streaming query recuperada a partir do mesmo checkpoint.

`runId` identifica uma execução específica da query.

Portanto:

```text
mesmo checkpoint
      ↓
mesma identidade lógica
      ↓
query.id permanece
```

Enquanto:

```text
novo start / restart
      ↓
nova execução
      ↓
runId muda
```

O UUID observado anteriormente em:

```text
checkpoint/metadata
```

está relacionado à identidade da streaming query mantida pelo checkpoint.

# O que está documentado oficialmente

A documentação oficial da Databricks estabelece que:

- checkpoints e write-ahead logs trabalham juntos para fornecer garantias de processamento em Structured Streaming;
- o checkpoint acompanha informações que identificam a query e os registros já processados;
- `offsets` registram os offsets da source processados em cada micro-batch;
- `commits` registram quais micro-batches foram commitados no sink;
- `metadata` contém o identificador único da query;
- consultas stateful também armazenam informações relacionadas ao estado;
- cada streaming query deve utilizar uma localização de checkpoint própria;
- alterar para uma nova localização de checkpoint ou apagar o checkpoint faz a próxima execução iniciar sem aquele progresso anterior;
- `checkpointLocation` pode apontar para um caminho persistente em um Unity Catalog Volume;
- algumas alterações entre reinicializações podem não ser compatíveis com a reutilização do mesmo checkpoint.

# O que foi observado no laboratório

No ambiente Databricks utilizado no laboratório:

1. A primeira carga possuía 30 registros.

2. A escrita da source com:

```python
.repartition(3)
```

produziu três arquivos Parquet observáveis no diretório `input/`.

3. Após a primeira execução, o checkpoint continha:

```text
sources/
offsets/
commits/
metadata
```

4. Dentro de `offsets/` foi observado:

```text
0
```

5. Dentro de `commits/` foi observado:

```text
0
```

6. O `metadata` apresentou um UUID.

7. Ao adicionar 20 novos registros à mesma source e executar novamente utilizando o mesmo checkpoint, a tabela original passou de 30 para 50 registros.

8. Ao utilizar um checkpoint novo e uma nova tabela destino, os 50 registros ainda disponíveis na source foram processados pela nova query e inseridos na nova tabela.

query.id

```text

```

# Interpretação baseada nas evidências

Os resultados são consistentes com o checkpoint atuando como memória persistente do progresso da streaming query.

A source e o checkpoint exercem funções diferentes:

```text
SOURCE
↓
contém os dados
```

```text
CHECKPOINT
↓
contém informações sobre o progresso da query
```

Por isso, quando um checkpoint novo foi utilizado, os dados antigos ainda existentes na source puderam ser processados novamente.

A nova query não recuperou dados do checkpoint antigo e também não recuperou dados da tabela destino antiga.

Ela leu novamente a mesma source.

---

# Principais aprendizados

1. **Checkpoint não é armazenamento dos dados da source.**

2. **Checkpoint mantém o progresso e informações necessárias à recuperação da streaming query.**

3. Reutilizar o mesmo checkpoint permite que uma nova execução recupere o progresso registrado anteriormente.

4. Utilizar um checkpoint novo significa iniciar uma nova identidade/progresso do ponto de vista da query.

5. Os dados só podem ser reprocessados se ainda estiverem disponíveis na source.

6. `INPUT_PATH` representa a source.

7. `CHECKPOINT_PATH` representa o diretório persistente de checkpoint.

8. `TARGET_TABLE` representa a tabela Delta de destino.

9. `query.id` identifica a streaming query e pode persistir entre reinicializações recuperadas pelo mesmo checkpoint.

10. `runId` identifica uma execução específica e muda a cada nova execução.

11. Os arquivos `offsets/0` e `commits/0` observados conectam diretamente o conceito de checkpoint aos micro-batches estudados no Lab 25.

---

# Conclusão

O Lab 26 mostrou experimentalmente que o checkpoint funciona como um mecanismo de persistência do progresso de uma consulta Structured Streaming.

Na primeira execução, o Spark processou os 30 registros disponíveis e criou estruturas de checkpoint contendo `sources`, `offsets`, `commits` e `metadata`.

Após a inclusão de novos dados, a reutilização do mesmo checkpoint permitiu que uma nova execução continuasse a partir do progresso anteriormente registrado.

Quando foi utilizado um checkpoint novo, a nova query não possuía aquele histórico e processou novamente os 50 registros que ainda estavam disponíveis na source, gravando-os em uma nova tabela Delta.

Por fim, a comparação entre `query.id` e `runId` mostrou que a identidade lógica da streaming query pode ser preservada pelo checkpoint, enquanto cada execução individual recebe uma identidade própria.

O laboratório também reforçou uma distinção fundamental para Structured Streaming:

```text
Source
→ onde estão os dados

Checkpoint
→ onde está o progresso da query

Sink
→ onde o resultado é gravado
```

Essa separação será importante nos próximos laboratórios da Fase 5, especialmente ao estudar Watermark, Late Data e Stateful Processing.
