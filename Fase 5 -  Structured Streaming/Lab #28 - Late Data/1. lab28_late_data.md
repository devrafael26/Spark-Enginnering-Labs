## Spark Engineering Lab 28 - Late Data

## Categoria

Structured Streaming

## Objetivo

Entender como o Apache Spark Structured Streaming trata eventos que chegam atrasados em relação ao `event_time`, como o watermark participa dessa decisão e em que condições um evento atrasado ainda pode ser processado ou pode ser considerado tarde demais para uma agregação stateful.

O laboratório também busca diferenciar claramente:

- `event_time`: momento em que o evento ocorreu na origem;
- momento de chegada/processamento no Spark;
- late data: evento que chega depois de outros eventos com `event_time` mais recente;
- watermark: limite temporal utilizado pelo Spark para controlar tolerância a atraso e retenção de estado.

---

## Pergunta

Como o Structured Streaming trata eventos que chegam atrasados em relação ao `event_time` e ao watermark?

---

## Conceitos principais

### Event time

O `event_time` representa o momento em que o evento efetivamente aconteceu na fonte.

Exemplo:

```text
Venda aconteceu: 10:08
Spark recebeu:    10:31
```

O `event_time` continua sendo `10:08`. O fato de o Spark receber o evento posteriormente caracteriza atraso na chegada, e não necessariamente erro no timestamp da origem.

### Late data

Late data é um evento que chega depois de o stream já ter observado eventos com `event_time` mais recente.

Exemplo:

```text
Ordem de chegada ao Spark:

10:05
10:12
10:30
10:08  <- late data
```

O evento `10:08` pode estar perfeitamente correto na fonte. O atraso pode ter ocorrido durante transporte, rede, Kafka, retry, indisponibilidade de produtor ou outro ponto da arquitetura.

### Watermark

Neste laboratório foi utilizado:

```python
.withWatermark("event_time", "10 minutes")
```

Os `10 minutes` são o `delayThreshold`, isto é, a tolerância configurada para dados atrasados.

Conceitualmente:

```text
watermark ~= MAX(event_time observado) - delayThreshold
```

Exemplo:

```text
MAX(event_time) = 10:30
delayThreshold  = 10 minutos

watermark ~= 10:20
```

O watermark fica para trás do maior `event_time` observado porque representa até onde o Spark ainda mantém tolerância para eventos antigos.

Ele não é calculado com `+ 10 minutos`, pois isso colocaria o limite à frente do maior horário de evento já observado.

# Experimento A - Baseline: eventos em ordem

## Objetivo

Estabelecer o comportamento normal da agregação por janela antes de provocar late data.

## Dados

Foram inseridos três eventos:

```text
10:01
10:03
10:20
```

Os eventos `10:01` e `10:03` pertencem à janela:

```text
10:00 -> 10:05
```

O evento `10:20` foi utilizado para avançar o maior `event_time` observado e, consequentemente, o watermark.

## Transformações

```python
df_agg_a = (
    df_stream_a
    .withWatermark("event_time", "10 minutes")
    .groupBy(
        F.window("event_time", "5 minutes")
    )
    .agg(
        F.count("*").alias("qtd_eventos")
    )
)
```

## Action

```python
queryA = (
    df_agg_a.writeStream
    .format("delta")
    .outputMode("append")
    .option("checkpointLocation", checkpointA)
    .trigger(availableNow=True)
    .toTable(targetA)
)

queryA.awaitTermination()
```

## Comando de análise

Foram observados:

```python
show_progress(queryA)
```

E o resultado final:

```python
display(
    spark.table(targetA)
    .orderBy("window.start")
)
```

## Resultado observado

A fonte continha corretamente três registros:

```text
10:01
10:03
10:20
```

O progresso mostrou:

```text
batchId = 0
inputRows = 3
watermark = 1970...
droppedByWatermark = 0

batchId = 1
inputRows = 0
watermark = 2026-09-21 10:10:00
droppedByWatermark = 0
```

O target apresentou:

```text
window.start = 10:00
window.end   = 10:05
qtd_eventos  = 2
```

## Interpretação

O evento de `10:20` fez o maior `event_time` observado avançar para `10:20`.

Com watermark de 10 minutos:

```text
10:20 - 10 min = 10:10
```

A janela `10:00 -> 10:05` passou a estar completamente atrás do watermark e pôde ser considerada finalizada.

Como o output mode utilizado foi `append`, o Spark gravou o resultado final da janela apenas após sua finalização.

# Experimento B - Late data ainda dentro da tolerância

## Objetivo

Demonstrar que um evento pode ser considerado late data e, ainda assim, ser processado normalmente quando permanece à frente do watermark vigente.

## Dados

Primeiro foi inserido:

```text
10:30
```

Depois foi inserido:

```text
10:24
```

Posteriormente foi inserido:

```text
10:40
```

## Sequência temporal observada

Após o primeiro evento:

```text
MAX(event_time) = 10:30
watermark ~= 10:20
```

O evento `10:24` chegou depois de o Spark já ter observado `10:30`.

Portanto:

```text
10:24 < 10:30
```

Ele é late data.

Porém:

```text
10:24 > 10:20
```

Ele ainda estava à frente do watermark.

## Resultado da Query B1

```text
inputRows = 1
watermark = 1970...

inputRows = 0
watermark = 10:20
```

O evento `10:30` foi efetivamente processado no primeiro batch (`inputRows = 1`).

O batch seguinte, sem novas linhas, refletiu o avanço do watermark para `10:20`.

## Resultado da Query B2

Depois da inserção do evento `10:24`:

```text
inputRows = 1
watermark = 10:20
droppedByWatermark = 0
```

O `inputRows = 1` corresponde ao evento `10:24`.

O resultado mostra que o evento foi processado e não foi descartado pelo watermark.

## Resultado da Query B3

Depois da inserção do evento `10:40`:

```text
batchId = 3
inputRows = 1
watermark = 10:20
droppedByWatermark = 0

batchId = 4
inputRows = 0
watermark = 10:30
droppedByWatermark = 0
```

O evento `10:40` tornou-se o novo máximo observado.

Conceitualmente:

```text
MAX(event_time) = 10:40
watermark ~= 10:30
```

## Resultado final

O target apresentou:

```text
window = 10:20 -> 10:25
qtd_eventos = 1
```

Esse registro corresponde ao evento:

```text
event_time = 10:24
```

## Conclusão do Experimento B

O evento `10:24` foi late data porque chegou após o Spark já ter observado `10:30`.

Entretanto, como o watermark vigente era `10:20`, ele ainda estava dentro da tolerância configurada e participou normalmente da agregação.

Portanto:

```text
late data != dado automaticamente descartado
```

# Experimento C - Evento anterior ao watermark

## Objetivo

Demonstrar o comportamento de um evento que chega com `event_time` anterior ao watermark vigente e observar a métrica `numRowsDroppedByWatermark`.

## Dados

Primeiro foi inserido:

```text
10:30
```

Depois:

```text
10:08
```

E posteriormente:

```text
10:40
```

## Query C1

O primeiro evento produziu:

```text
inputRows = 1
watermark = 1970...

inputRows = 0
watermark = 10:20
```

Com:

```text
MAX(event_time) = 10:30
```

passamos a ter conceitualmente:

```text
watermark ~= 10:20
```

## Query C2 - Evento muito atrasado

Foi então inserido:

```text
event_time = 10:08
```

A saída mostrou:

```text
inputRows = 1
watermark = 10:20
droppedByWatermark = 1
```

Como:

```text
10:08 < 10:20
```

o evento estava atrás do watermark vigente.

A métrica:

```text
numRowsDroppedByWatermark = 1
```

forneceu evidência de que uma linha foi considerada tarde demais para a agregação stateful.

## Query C3 - Avanço posterior do event time

Foi inserido:

```text
10:40
```

A saída mostrou:

```text
batchId = 3
inputRows = 1
watermark = 10:20
droppedByWatermark = 0

batchId = 4
inputRows = 0
watermark = 10:30
droppedByWatermark = 0
```

O novo máximo passou a ser:

```text
MAX(event_time) = 10:40
```

Logo, o watermark avançou posteriormente para aproximadamente:

```text
10:30
```

## Resultado final

Ao consultar o target:

```text
no rows returned
```

Esse comportamento foi coerente com o experimento.

O evento `10:08` foi descartado pela agregação stateful, evidenciado por:

```text
droppedByWatermark = 1
```

Já o evento `10:40` foi aceito (`inputRows = 1`, `dropped = 0`), porém pertence à janela:

```text
10:40 -> 10:45
```

Quando o watermark avançou para `10:30`, essa janela ainda não estava finalizada.

Como o output mode era `append`, nenhum resultado parcial foi emitido para o target.

# Observações importantes

## 1. O watermark não volta para trás

Se o Spark já observou:

```text
MAX(event_time) = 10:30
watermark ~= 10:20
```

E posteriormente chegam:

```text
10:25
10:19
```

nenhum deles altera o maior `event_time` observado.

Portanto:

```text
MAX(10:30, 10:25) = 10:30
MAX(10:30, 10:19) = 10:30
```

O watermark permanece aproximadamente em `10:20`.

O evento antigo não faz o watermark voltar para `10:09`.

Para o watermark avançar, é necessário observar um novo máximo.

Exemplo:

```text
novo event_time = 10:40

MAX = 10:40
watermark ~= 10:30
```

### Interpretação

O watermark funciona como um relógio lógico associado ao progresso do `event_time` observado pelo stream. Eventos antigos não fazem esse relógio retroceder.

---

## 2. Os 10 minutos são configuração; 10:20 e 10:30 são valores calculados

Neste laboratório:

```python
.withWatermark("event_time", "10 minutes")
```

O valor configurado foi:

```text
10 minutos
```

Já valores como:

```text
10:20
10:30
```

foram valores correntes do watermark observados durante a execução.

Exemplo:

```text
MAX = 10:30 -> watermark ~= 10:20
MAX = 10:40 -> watermark ~= 10:30
```

---

## 3. Watermark e window são conceitos diferentes

Neste laboratório:

```text
watermark = 10 minutos
window    = 5 minutos
```

A window responde:

> Em qual intervalo temporal o evento será agregado?

O watermark responde:

> Até quanto atraso em event time a operação stateful está preparada para tolerar/manter estado?

Exemplo:

```text
event_time = 10:24
```

pertence à janela:

```text
10:20 -> 10:25
```

Isso é independente do fato de o watermark naquele momento ser `10:20`.

---

## 4. O watermark é baseado em event time, não no relógio do Spark

Quando foi observado:

```text
MAX(event_time) = 10:30
```

isso significava que `10:30` era o maior timestamp presente na coluna `event_time` já observada pelo stream.

Não significava que o Spark estava executando exatamente às `10:30`.

---

## 5. Late data não significa event_time incorreto

Um evento pode ter:

```text
event_time correto = 10:08
```

mas chegar ao Spark depois de eventos com timestamps maiores.

Exemplo:

```text
10:05
10:12
10:30
10:08
```

A desordem pode estar na entrega dos eventos, e não no timestamp da origem.

---

## 6. Evento atrás do watermark não significa que o dado foi apagado da origem

No Experimento C, `droppedByWatermark = 1` indicou que o operador stateful considerou uma linha tarde demais para aquela agregação.

Isso não significa necessariamente que o registro tenha sido fisicamente removido da fonte.

Se o dado veio, por exemplo, de Kafka ou de uma tabela Delta, ele pode continuar existindo na camada de origem/raw.

O descarte está relacionado ao processamento daquela operação stateful.

Em arquiteturas reais, especialmente para eventos importantes como vendas, pode ser necessário desenhar estratégias adicionais de:

- retenção na camada raw/bronze;
- auditoria;
- reconciliação;
- reprocessamento;
- tratamento separado de late events.

O Spark não envia automaticamente esses registros para uma DLQ ou tabela de rejeitados apenas porque ficaram atrás do watermark.

---

## 7. `inputRows = 0` em um batch não significa que nada relevante aconteceu

Nos experimentos foi observado um padrão como:

```text
batch N
inputRows = 1
watermark = valor anterior

batch N+1
inputRows = 0
watermark = valor atualizado
```

O batch sem novas linhas permitiu observar o avanço do watermark e, em alguns casos, a finalização de janelas antigas.

Portanto, um micro-batch com `inputRows = 0` pode ainda representar uma mudança relevante no estado temporal da query.

---

## 8. `append` só emite resultados finalizados

Como o laboratório utilizou:

```python
.outputMode("append")
```

os resultados de uma agregação por janela não foram enviados ao target enquanto ainda poderiam receber atualizações.

A janela só apareceu no target depois que o watermark ultrapassou seu final.

Isso explicou:

- o resultado do Experimento A;
- a emissão da janela `10:20 -> 10:25` no Experimento B;
- o `no rows returned` no Experimento C.

---

# O que está documentado oficialmente

A documentação oficial do Apache Spark e da Databricks estabelece que:

- `withWatermark(eventTime, delayThreshold)` define um watermark sobre uma coluna de event time;
- o watermark corrente é calculado com base no maior `eventTime` observado menos o `delayThreshold` configurado;
- watermarks são usados para controlar a quantidade de estado mantida por operações stateful;
- em agregações por janela com output mode `append`, resultados são emitidos quando as janelas são consideradas finalizadas pelo watermark;
- `numRowsDroppedByWatermark` indica linhas consideradas tardias demais para serem incluídas em uma agregação stateful, embora a própria Databricks ressalte que essa métrica não é perfeitamente precisa.

# Interpretação baseada nas evidências

Os experimentos demonstraram de forma prática que late data deve ser analisado em relação ao watermark vigente, e não apenas em relação ao maior `event_time` observado.

Um evento pode ser atrasado e ainda ser aceito:

```text
MAX = 10:30
watermark = 10:20
late event = 10:24

10:24 > 10:20
```

Por outro lado, um evento muito antigo pode ser considerado tarde demais pela operação stateful:

```text
MAX = 10:30
watermark = 10:20
late event = 10:08

10:08 < 10:20
```

No laboratório, essa diferença foi evidenciada diretamente pela métrica `numRowsDroppedByWatermark`.

---

# Conclusão

O Lab 28 mostrou que late data não é simplesmente "um evento antigo" nem significa automaticamente perda de informação.

O comportamento depende da relação entre:

```text
event_time
+
maior event_time já observado
+
delayThreshold configurado
+
watermark vigente
+
janela stateful
+
output mode
```

O principal aprendizado foi:

> O watermark cria um limite temporal baseado no progresso do `event_time`. Eventos atrasados que ainda estejam dentro da tolerância podem ser processados normalmente. Eventos que chegam tarde demais podem deixar de participar da agregação stateful, e esse comportamento pode ser observado por métricas como `numRowsDroppedByWatermark`.

Também foi observado que o watermark não retrocede quando chega um evento antigo. Ele avança conforme surgem novos máximos de `event_time`.

Em cenários reais, principalmente quando os eventos representam informações críticas como vendas, o watermark deve ser configurado considerando o atraso legítimo esperado dos dados e a necessidade de retenção, auditoria e eventual reprocessamento.
