## Spark Engineering Lab 27 - Watermark

## Categoria

Structured Streaming

---

## Objetivo

Entender como o Apache Spark Structured Streaming utiliza **watermark** para controlar até quando estados antigos precisam ser mantidos em operações stateful baseadas em **event time**, observando na prática:

- a criação de janelas temporais com base em `event_time`;
- a aplicação de watermark;
- o avanço do watermark entre micro-batches;
- a relação entre watermark e estado;
- a remoção de estado antigo;

## Pergunta

Como o Structured Streaming utiliza watermark para estabelecer um limite temporal e controlar por quanto tempo o estado de janelas antigas precisa ser mantido?

Perguntas complementares:

- Como o `event_time` determina a qual janela um evento pertence?
- Como uma janela de 5 minutos se relaciona com um watermark de 10 minutos?
- Como observar o avanço do watermark entre micro-batches?
- Como identificar o impacto desse avanço sobre o estado da query?
- Como adaptar o experimento às limitações do Databricks Serverless?

# Conceito

Watermark é um mecanismo utilizado pelo Structured Streaming para controlar o tratamento de dados atrasados e, principalmente, permitir que o mecanismo de execução determine quando estados antigos podem ser removidos.

O watermark é configurado sobre uma coluna de **event time**.

Exemplo:

```python
.withWatermark("event_time", "10 minutes")
```

A ideia conceitual é:

```text
maior event_time observado
        -
delayThreshold
        =
watermark
```

Exemplo conceitual:

```text
MAX(event_time) = 10:18
delayThreshold  = 10 min

watermark ≈ 10:08
```

A janela e o watermark possuem funções diferentes.

```text
window
↓
define a qual intervalo temporal
cada evento pertence
```

```text
watermark
↓
ajuda a determinar até quando
o estado de períodos antigos
precisa continuar sendo mantido
```

Por exemplo:

```text
window = 5 minutos
watermark = 10 minutos
```

Uma janela pode ser:

```text
10:00 ───────── 10:05
```

Um evento com:

```text
event_time = 10:03
```

pertence sempre à janela:

```text
10:00–10:05
```

O watermark não muda a janela à qual o evento pertence.

O watermark controla até quando o Spark precisa continuar mantendo o estado associado àquela janela.

# Experimento A - Event Time + Window sem Watermark

## Objetivo

Verificar se o `event_time` determina corretamente a janela temporal na qual cada registro será agregado.

---

## Dados

Foram criados seis registros com horários controlados.

```python
dados_a = [
    (1, "2026-09-18 10:01:00"),
    (2, "2026-09-18 10:02:00"),
    (3, "2026-09-18 10:04:00"),
    (4, "2026-09-18 10:06:00"),
    (5, "2026-09-18 10:08:00"),
    (6, "2026-09-18 10:11:00"),
]
```

Tabela fonte:

```text
lab27_source_a
```

---

## Código

```python
from pyspark.sql import functions as F

spark.sql("DROP TABLE IF EXISTS lab27_source_a")

dados_a = [
    (1, "2026-09-18 10:01:00"),
    (2, "2026-09-18 10:02:00"),
    (3, "2026-09-18 10:04:00"),
    (4, "2026-09-18 10:06:00"),
    (5, "2026-09-18 10:08:00"),
    (6, "2026-09-18 10:11:00"),
]

df_a = (
    spark.createDataFrame(
        dados_a,
        ["event_id", "event_time"]
    )
    .withColumn(
        "event_time",
        F.to_timestamp("event_time")
    )
)

df_a.write.mode("overwrite").saveAsTable("lab27_source_a")
```

Validação:

```python
spark.table("lab27_source_a").orderBy("event_time").show(truncate=False)
```

Leitura como streaming:

```python
stream_a = (
    spark.readStream
        .table("lab27_source_a")
)
```

Agregação por janela de 5 minutos:

```python
window_a = (
    stream_a
        .groupBy(
            F.window("event_time", "5 minutes")
        )
        .count()
)
```

Execução:

```python
query_a = (
    window_a.writeStream
        .format("memory")
        .queryName("lab27_result_a")
        .outputMode("complete")
        .option(
            "checkpointLocation",
            "/Volumes/workspace/default/lab27_checkpoints/lab27_exp_a"
        )
        .trigger(availableNow=True)
        .start()
)

query_a.awaitTermination()
```

Consulta do resultado:

```python
spark.sql("""
SELECT
    window.start AS window_start,
    window.end   AS window_end,
    count
FROM lab27_result_a
ORDER BY window_start
""").show(truncate=False)
```

---

## Resultado observado

```text
10:00–10:05 → 3 eventos
10:05–10:10 → 2 eventos
10:10–10:15 → 1 evento
```

Distribuição:

```text
10:01
10:02
10:04
      ↓
10:00–10:05
count = 3
```

```text
10:06
10:08
      ↓
10:05–10:10
count = 2
```

```text
10:11
      ↓
10:10–10:15
count = 1
```

---

## Observação

O parâmetro:

```python
F.window("event_time", "5 minutes")
```

não significa que a query será executada a cada cinco minutos.

Ele define o tamanho das janelas utilizadas para agrupar os eventos de acordo com o valor da coluna `event_time`.

---

## Conclusão do Experimento A

O experimento confirmou que o `event_time` determina corretamente a janela temporal à qual cada registro pertence.

O resultado observado foi compatível com as faixas de 5 minutos definidas pela função `window`.

## Por que `coalesce(1)`?

O `coalesce(1)` foi utilizado como estratégia experimental para reduzir o número de partições antes da escrita e favorecer a geração de uma quantidade pequena de arquivos físicos por lote.

Isso facilitou a combinação com:

```python
maxFilesPerTrigger = 1
```

O uso de `coalesce(1)` neste laboratório não representa uma regra geral de produção.

Ele foi utilizado para tornar o comportamento da leitura mais controlado e observável.

## Streaming Query

Versão consolidada em um único bloco:

```python
query_b = (
    spark.readStream
        .option("maxFilesPerTrigger", 1)
        .table("lab27_source_b")
        .withWatermark("event_time", "10 minutes")
        .groupBy(
            F.window("event_time", "5 minutes")
        )
        .count()
        .writeStream
        .format("memory")
        .queryName("lab27_result_b")
        .outputMode("update")
        .option(
            "checkpointLocation",
            "/Volumes/workspace/default/lab27_checkpoints/lab27_exp_b"
        )
        .trigger(availableNow=True)
        .start()
)

query_b.awaitTermination()
```

## `maxFilesPerTrigger`

Configuração utilizada:

```python
.option("maxFilesPerTrigger", 1)
```

Significado:

```text
cada micro-batch
      ↓
pode considerar no máximo
1 novo arquivo físico
da fonte Delta
```

Exemplo conceitual:

```text
arquivo 1
arquivo 2
arquivo 3
arquivo 4
      ↓
AvailableNow
      ↓
micro-batch 0 → até 1 arquivo
micro-batch 1 → até 1 arquivo
micro-batch 2 → até 1 arquivo
micro-batch 3 → até 1 arquivo
      ↓
backlog processado
      ↓
query encerra
```

O `maxFilesPerTrigger` não define a quantidade total de micro-batches.

Ele limita a quantidade máxima de novos arquivos considerados em cada micro-batch.

---

## `AvailableNow`

No ambiente Serverless foi utilizado:

```python
.trigger(availableNow=True)
```

Conceitualmente:

```text
AvailableNow
=
processar todo o backlog
disponível naquele momento
e depois encerrar
```

O backlog pode ser dividido em vários micro-batches.

---

## Memory Sink

A saída foi definida como:

```python
.format("memory")
.queryName("lab27_result_b")
```

Portanto:

```text
lab27_result_b
```

é uma saída temporária em memória utilizada para inspeção do resultado da streaming query.

Não é uma tabela Delta persistida.

A tabela Delta real utilizada como fonte é:

```text
lab27_source_b
```

O checkpoint também não é o resultado.

Ele possui outra função:

```text
checkpoint
↓
progresso
offsets
commits
estado
metadados necessários
para continuidade da query
```

# Análise do State Store

Código:

```python
for p in query_b.recentProgress:

    print("=" * 60)
    print("Batch ID:", p.get("batchId"))

    state_operators = p.get("stateOperators", [])

    if not state_operators:
        print("Nenhum state operator reportado.")
        continue

    for i, state in enumerate(state_operators):

        print(f"\nState Operator {i}")

        print(
            "numRowsTotal:",
            state.get("numRowsTotal")
        )

        print(
            "numRowsUpdated:",
            state.get("numRowsUpdated")
        )

        print(
            "numRowsRemoved:",
            state.get("numRowsRemoved")
        )

        print(
            "memoryUsedBytes:",
            state.get("memoryUsedBytes")
        )

      ↓

      ↓

      ↓
writeStream
      ↓

```

O:

```python
.start()
```

inicia efetivamente a streaming query.

# O que está documentado oficialmente

A documentação oficial do Apache Spark e da Databricks estabelece que:

- watermarks são utilizados em operações stateful para limitar o tempo durante o qual estados antigos precisam ser mantidos;
- o watermark é associado a uma coluna de event time;
- o delay threshold define a tolerância de atraso;
- `AvailableNow` processa os dados disponíveis e encerra a query;
- `maxFilesPerTrigger` limita o número de novos arquivos considerados em cada micro-batch;
- `stateOperators` expõe métricas do estado da query;
- `numRowsTotal` representa a quantidade de linhas mantidas no estado;
- `numRowsUpdated` representa linhas de estado atualizadas;
- `numRowsRemoved` representa linhas removidas do estado;
- `memoryUsedBytes` indica memória utilizada pelo state store;
- checkpoint é utilizado para armazenar progresso, offsets, commits, metadados e estado necessários para recuperação e continuidade da query.

# O que foi observado no laboratório

Foi observado que:

- o `event_time` distribuiu corretamente os registros nas janelas de 5 minutos;
- a query com `AvailableNow` foi dividida em múltiplos micro-batches;
- o `eventTime.max` avançou conforme novos lotes foram processados;
- o watermark avançou progressivamente;
- batches sem novos registros ainda apresentaram avanço do watermark;
- `numRowsTotal` aumentou de 1 para 4 conforme novas janelas passaram a ser mantidas;
- `numRowsRemoved` permaneceu em 0 até o watermark avançar suficientemente;
- no Batch 5, `numRowsRemoved = 1`;
- no mesmo batch, `numRowsTotal` caiu de 4 para 3;
- o comportamento observado foi consistente com a remoção de estado antigo após avanço do watermark;
- `numInputRows` retornou `None` pela forma de acesso utilizada;
- o Serverless exigiu checkpoint explícito;
- `ProcessingTime` não foi suportado naquele tipo de compute;
- `AvailableNow` foi utilizado como alternativa compatível.

# Interpretação baseada nas evidências

Os resultados indicam que o watermark não atua apenas como uma configuração declarativa.

Ele possui efeito direto sobre o gerenciamento de estado da query.

No experimento, o comportamento observado foi consistente com:

```text
event_time avançando
      ↓
watermark avançando
      ↓
janela antiga ficando atrás do watermark
      ↓
remoção de estado
```

A queda:

```text
numRowsTotal: 4 → 3
```

simultaneamente ao aumento:

```text
numRowsRemoved: 0 → 1
```

foi a principal evidência experimental dessa relação.

Não se deve transformar esse resultado específico em uma regra universal sobre quantos batches são necessários para um watermark avançar ou exatamente quando uma linha específica será removida em qualquer workload.

O comportamento deve sempre ser analisado levando em consideração a query, a distribuição dos dados, a fonte, os triggers e o ambiente de execução.
