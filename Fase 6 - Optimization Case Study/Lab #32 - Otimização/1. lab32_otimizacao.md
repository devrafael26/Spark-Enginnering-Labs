---

## Objetivo

Aplicar otimizações orientadas pelo diagnóstico realizado no Lab #31, evitando otimizações genéricas ou sem evidência de necessidade.

> Quais otimizações realmente fazem sentido quando aplicadas aos gargalos identificados na pipeline do Lab #30?

A ideia principal foi diferenciar:

- otimizações que o próprio Spark/Databricks já realiza automaticamente;
- intervenções manuais que não alteram de forma relevante o plano físico;

# Experimento A - Reescrita explícita de filtros e projeções

## Conclusão do Experimento A

A reorganização manual da pipeline tornou o código mais alinhado ao plano lógico otimizado, porém não produziu uma mudança relevante na estratégia física.

O Catalyst já realizava no baseline:

- antecipação de filtros;
- column pruning;
- escolha automática de Broadcast Hash Join;
- uso de Photon;
- agregação parcial antes do Shuffle.

A principal conclusão foi:

```text
Código aparentemente mais otimizado
≠
novo plano físico necessariamente melhor
```

Uma reescrita manual pode melhorar clareza e legibilidade do código, mas não implica automaticamente melhoria física quando o otimizador já produz uma estratégia equivalente.

# Experimento B - Liquid Clustering e Data Skipping

## Objetivo

Atacar o principal custo de tempo identificado no diagnóstico:

```text
Scan
≈ 87,6% do Time Spent
```

A hipótese foi:

> Se a tabela principal for fisicamente organizada por `order_date`, o filtro em `order_date` poderá se beneficiar de data skipping mais eficiente.

---

# Conceito - Data Skipping

Data skipping é um mecanismo automático utilizado durante a leitura.

A engine pode utilizar estatísticas por arquivo, como:

```text
min
max
null count
row count
```

para identificar arquivos que não podem conter registros relevantes para um determinado filtro.

Exemplo conceitual:

```text
Arquivo A → Jan / Fev
Arquivo B → Mar / Abr
Arquivo C → Mai / Jun
Arquivo D → Jul / Ago
```

Consulta:

```text
order_date >= 2026-07-01
```

Pode permitir:

```text
Arquivo A → ignorado
Arquivo B → ignorado
Arquivo C → ignorado
Arquivo D → lido
```

Data skipping não é acionado manualmente por função específica na query.

Ele ocorre automaticamente quando:

- existem estatísticas apropriadas;
- o filtro permite eliminar arquivos;
- o layout dos dados torna essas estatísticas úteis.

---

# Conceito - Liquid Clustering

Liquid Clustering é uma técnica de organização física dos dados de uma tabela.

Exemplo:

```sql
CLUSTER BY (order_date)
```

A intenção é melhorar o agrupamento físico dos valores da clustering key, favorecendo operações como data skipping.

Relação conceitual:

```text
Liquid Clustering
        ↓
organização física dos dados
        ↓
estatísticas por arquivo mais úteis
        ↓
Data Skipping
        ↓
menos arquivos precisam ser lidos
```

Importante:

```text
Liquid Clustering
≠
Data Skipping
```

Liquid Clustering é layout físico.

Data Skipping é o mecanismo automático de leitura que pode ignorar arquivos.

### Documentação oficial

Databricks - Liquid Clustering:

https://docs.databricks.com/aws/en/delta/clustering.html

Databricks - Data Skipping:

https://docs.databricks.com/aws/en/delta/data-skipping.html

## Criação da massa

```python
from pyspark.sql import functions as F

orders_large = (
    spark.range(300_000_000)
    .withColumn("customer_id", (F.col("id") % 1_000_000).cast("long"))
    .withColumn("product_id", (F.col("id") % 50_000).cast("long"))
    .withColumn("quantity", ((F.col("id") % 5) + 1).cast("int"))
    .withColumn("amount", ((F.col("id") % 1000) / 10.0).cast("double"))
    .withColumn(
        "order_status",
        F.when((F.col("id") % 10) < 7, "COMPLETED").otherwise("PENDING")
    )
    .withColumn(
        "order_date",
        F.date_add(
            F.lit("2026-01-01"),
            (F.col("id") % 270).cast("int")
        )
    )
    .drop("id")
)
```

)

# Data Skew e Skew Handling

Durante a discussão do laboratório foi feita uma distinção importante.

## Data Skew

É o problema de distribuição desigual dos dados entre chaves ou partições.

Esse conceito foi estudado diretamente no Lab #12.

## Skew Handling

É uma forma de tratamento para determinados casos de skew.

O AQE pode tratar partições skewed em determinados joins baseados em Shuffle.

Entretanto, no Lab #30/#31 os joins observados foram:

```text
PhotonBroadcastHashJoin
```

Portanto, não havia evidência para aplicar uma intervenção específica de skew handling no Lab #32.

A decisão foi:

```text
skew existe nos dados
≠
skew comprovado como gargalo da execução
```

Logo, nenhuma otimização específica para skew foi aplicada.

# Conclusão

O Lab #32 mostrou que otimização em Spark não deve ser tratada como uma lista de técnicas aplicadas automaticamente a qualquer pipeline.

O raciocínio utilizado foi:

```text
Diagnóstico
    ↓
Identificar gargalo real
    ↓
Verificar o que o engine já otimiza
    ↓
Evitar intervenções desnecessárias
    ↓
Aplicar mudança direcionada
    ↓
Medir evidências
    ↓
Validar resultado lógico
```

O Experimento A demonstrou que o Catalyst já resolvia várias aparentes ineficiências do código original.

O Experimento B mostrou que, quando o gargalo observado estava relacionado ao Scan, atuar no layout físico da tabela pôde tornar o Data Skipping mais efetivo.

O Experimento C confirmou que a otimização não alterou a regra de negócio.

A principal conclusão do laboratório é:

> Performance Engineering não significa aplicar broadcast, repartition, cache, clustering ou qualquer outra técnica de forma automática. Significa diagnosticar a execução, identificar evidências, escolher uma intervenção coerente com o gargalo observado e validar se o resultado permaneceu correto.
