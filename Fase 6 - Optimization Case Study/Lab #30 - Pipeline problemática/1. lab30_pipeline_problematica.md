## Estrutura inicial da pipeline

A pipeline foi escrita originalmente com a seguinte ordem lógica:

```text
orders
  ↓
JOIN customers
  ↓
JOIN products
  ↓
FILTER
  ↓
GROUP BY
  ↓
AGG
  ↓
WRITE DELTA
```

Os filtros foram propositalmente definidos depois dos joins no código.

---

## Regra de negócio

A pipeline calcula métricas por:

- `region_id`
- `category_id`

Considerando apenas:

- pedidos `COMPLETED`;
- clientes `ACTIVE`;
- pedidos com `order_date >= 2026-07-01`.

Métricas:

- `total_revenue`
- `total_units`
- `total_orders`
- `avg_order_value`

---

## Transformações

```python
pipeline_baseline = (
    orders_df

    .join(
        customers_df,
        on="customer_id",
        how="inner"
    )

    .join(
        products_df,
        on="product_id",
        how="inner"
    )

    .filter(
        (F.col("order_status") == "COMPLETED") &
        (F.col("customer_status") == "ACTIVE") &
        (F.col("order_date") >= F.lit("2026-07-01"))
    )

    .groupBy(
        "region_id",
        "category_id"
    )

    .agg(
        F.sum("amount").alias("total_revenue"),
        F.sum("quantity").alias("total_units"),
        F.count("*").alias("total_orders"),
        F.avg("amount").alias("avg_order_value")
    )
)
```

## Action

A execução foi disparada pela escrita da pipeline em uma tabela Delta.

```python
start = perf_counter()

pipeline_baseline.write \
    .format("delta") \
    .mode("overwrite") \
    .saveAsTable(result_table)

elapsed = perf_counter() - start

print(f"Tempo da pipeline baseline: {elapsed:.3f} s")
```

A chamada `saveAsTable()` materializou toda a pipeline.

# Skew

Foi criado skew proposital em:

```text
customer_id
```

A lógica utilizada na criação de `orders` foi:

```python
.withColumn(
    "customer_id",
    F.when(
        (F.col("order_id") % 10) < 4,
        F.col("order_id") % 100
    )
    .otherwise(
        F.col("order_id") % 1_000_000
    )
    .cast("long")
)
```

A condição:

```text
order_id % 10 < 4
```

seleciona aproximadamente 40% das linhas.

Entretanto, devido à combinação dessa condição com:

```text
order_id % 100
```

as linhas concentradas não são distribuídas entre 100 chaves diferentes.

Os valores possíveis nesse ramo são:

```text
0, 1, 2, 3,
10, 11, 12, 13,
20, 21, 22, 23,
...
90, 91, 92, 93
```

Portanto, o skew proposital foi concentrado em:

```text
40 hot keys de customer_id
```

e não em 100.

---

## Validação experimental do skew

A primeira validação utilizada foi:

```python
(
    spark.table(orders_table)
    .groupBy("customer_id")
    .count()
    .orderBy(F.desc("count"))
    .show(20, truncate=False)
)
```

As 20 primeiras linhas exibidas apresentaram:

```text
count = 300.000
```

Esse resultado já indicava a existência de chaves muito mais frequentes, porém o `show(20)` exibia apenas as maiores chaves e não tornava visível o contraste com os `customer_id` de baixa frequência.

Para tornar a distribuição mais clara, a validação pode ser complementada por:

```python
customer_distribution = (
    spark.table(orders_table)
    .groupBy("customer_id")
    .count()
)

customer_distribution     .groupBy("count")     .count()     .orderBy(F.desc("count"))     .show(truncate=False)
```

Pela própria regra de geração dos dados, a distribuição esperada é:

```text
40 hot keys
→ 300.000 registros por customer_id

aproximadamente 600.000 customer_ids regulares
→ 30 registros por customer_id
```

A concentração pode ser entendida por:

```text
30.000.000 × 40%
= 12.000.000 registros

12.000.000 / 40 hot keys
= 300.000 registros por hot key
```

Comparando uma hot key com uma chave regular:

```text
300.000 / 30
= 10.000x
```

Assim, o dataset possui um skew proposital bastante forte em `customer_id`.

---

## Comportamento do skew no plano físico

Apesar do skew comprovado nos dados, o join por `customer_id` foi executado como:

```text
PhotonBroadcastHashJoin
```

Não houve evidência, neste Lab, de um grande Shuffle da tabela `orders` por `customer_id`.

---

## Conclusão sobre o skew

O dataset possui skew e sua existência foi comprovada pela distribuição de frequências dos `customer_id`.

Entretanto:

```text
skew nos dados
≠
skew problemático comprovado na execução
```

Neste Lab não foi observada evidência suficiente para concluir que o skew criado provocou um gargalo relevante no join.

A estratégia física escolhida foi `PhotonBroadcastHashJoin`, portanto o simples fato de existir forte concentração nas chaves não significa, por si só, que ocorreu um skew join problemático nesta execução.

# O que foi observado

Neste experimento foi observado que:

1. a pipeline foi escrita com filtros após os joins;
2. o Catalyst reorganizou o plano e antecipou os filtros;
3. o Spark/Photon eliminou colunas desnecessárias dos scans;
4. os dois joins foram executados como `PhotonBroadcastHashJoin`;
5. `products` e `customers` foram utilizados como `BuildRight`;
6. ambos possuíam ramos `EXECUTOR_BROADCAST`;
7. os 30 milhões de registros de `orders` foram reduzidos para aproximadamente 10,56 milhões antes dos joins;
8. os joins mantiveram a cardinalidade em aproximadamente 10,56 milhões;
9. a agregação utilizou processamento parcial, Shuffle e agregação final;
10. o Shuffle da agregação utilizou `hashpartitioning(region_id, category_id, 37)`;
11. a tabela final possui 70 linhas;
12. o benchmark baseline foi de 7,441 segundos;
13. `Scan` concentrou 87,6% do `Time Spent`;
14. `Shuffle` concentrou 87,2% do `Memory Peak`;
15. o skew em `customer_id` foi comprovado experimentalmente, com 40 hot keys chegando a 300.000 registros cada, mas não se manifestou como um problema de join comprovado neste plano;
16. o plano exibido pelo `explain(True)` era o plano adaptativo inicial, com `isFinalPlan=false`.

# O que está documentado oficialmente

A documentação do Spark/Databricks descreve mecanismos de otimização de consultas que podem:

- reorganizar operações;
- aplicar filtros antecipadamente;
- reduzir colunas desnecessárias;
- selecionar estratégias de join;
- utilizar Broadcast Hash Join quando apropriado;
- utilizar Photon para operadores suportados;
- executar agregações distribuídas envolvendo Shuffle;
- utilizar Adaptive Query Execution para alterar planos durante a execução.

Neste laboratório, entretanto, as conclusões foram baseadas principalmente no plano e nas métricas efetivamente observadas na execução.

---

# Interpretação

A principal hipótese inicial era que a pipeline teria comportamento ruim porque os filtros foram escritos depois dos joins.

Essa hipótese não se confirmou da forma esperada.

O Catalyst reorganizou a consulta e antecipou os filtros.

Além disso, Photon selecionou Broadcast Hash Join para as duas dimensões.

Portanto, grande parte dos problemas artificiais introduzidos no código foi automaticamente mitigada antes ou durante a execução física.

O principal aprendizado é:

```text
código aparentemente ineficiente
≠
plano físico necessariamente ineficiente
```

O diagnóstico de performance não deve ser realizado apenas olhando o código PySpark.

É necessário observar:

```text
código
   ↓
Optimized Logical Plan
   ↓
Physical Plan
   ↓
Query Profile
   ↓
métricas reais
```

---

# Conclusão

A pipeline do Lab 30 foi construída propositalmente com características potencialmente ineficientes, incluindo filtros posicionados após os joins e skew em `customer_id`.

Entretanto, o Catalyst antecipou os filtros e reduziu as colunas necessárias, enquanto Photon executou os dois joins como Broadcast Hash Join utilizando `products` e `customers` como `BuildRight`.

Como consequência, os 30 milhões de registros de `orders` não foram levados integralmente aos joins. O Query Profile mostrou aproximadamente 10,56 milhões de registros passando pelos joins.

Assim, uma parte importante dos problemas introduzidos no código foi automaticamente mitigada pelo mecanismo de otimização.

Ainda assim, a execução apresentou pontos que merecem investigação:

```text
Time Spent
→ Scan = 87,6%

Memory Peak
→ Shuffle = 87,2%
```

Portanto, o Lab 30 não terminou com a conclusão de que a pipeline está totalmente otimizada.

Ele estabeleceu uma baseline e revelou que os problemas reais da execução não são necessariamente aqueles aparentes no código fonte.
