## Spark Engineering Lab 31 - Diagnóstico da Pipeline

## Categoria

Optimization Case Study

## Objetivo

Diagnosticar a execução da pipeline problemática construída no Lab 30, identificando quais pontos realmente aparecem como gargalos na execução e quais problemas inicialmente suspeitos foram mitigados pelo próprio Spark/Databricks.

O foco deste laboratório não é aplicar otimizações, mas interpretar as evidências fornecidas pelo plano de execução e pelo Query Profile.

---

## Pergunta

**Quais são os gargalos reais da pipeline do Lab 30 quando analisamos o plano de execução e as métricas de runtime?**

---

## Experimento

O Lab 31 reutiliza a execução produzida no Lab 30.

A pipeline analisada realiza:

1. leitura da tabela de pedidos;
2. join com clientes;
3. join com produtos;
4. aplicação de filtros;
5. agregação por região e categoria;
6. escrita do resultado final.

Nenhuma otimização adicional foi aplicada neste laboratório.

O objetivo foi analisar a execução já produzida utilizando:

- `explain(True)`;
- Query Profile - Rows;
- Query Profile - Time Spent;
- Query Profile - Memory Peak.

---

A tabela principal de pedidos foi criada com aproximadamente 30 milhões de registros.

A execução analisada produziu:

- **Linhas finais:** 70

## Comando de análise

```python
df_final.explain(True)
```

# Experimento A - Análise do Optimized Logical Plan

## Evidência observada

No plano analisado, os filtros aparecem inicialmente após os joins.

Entretanto, no `Optimized Logical Plan`, os filtros foram antecipados para perto das respectivas fontes de dados.

Na tabela `orders`, foram observados os filtros:

```text
order_date >= 2026-07-01
order_status = COMPLETED
```

Na tabela `customers`:

```text
customer_status = ACTIVE
```

Também foi observada eliminação de colunas desnecessárias por meio das projeções do plano.

Exemplo observado em `orders`:

```text
customer_id
product_id
quantity
amount
```

são mantidas para as etapas posteriores do plano.

## Diagnóstico

A ordem escrita no código não foi seguida literalmente pelo plano otimizado.

O Spark reorganizou o processamento para aplicar filtros antes dos joins e carregar apenas as colunas necessárias para as etapas seguintes.

Isso mostra que uma pipeline aparentemente problemática no código pode ser parcialmente corrigida pelo otimizador antes da execução física.

---

# Experimento B - Estratégia dos Joins

## Evidência observada

O plano físico mostrou dois operadores:

```text
PhotonBroadcastHashJoin
BuildRight
```

O primeiro join relacionou `orders` com `products`.

O segundo relacionou o resultado com `customers`.

No Query Profile, os joins processaram aproximadamente:

```text
10.56 M rows
```

Tempo associado aos joins:

```text
Inner Join customer_id: 622 ms
Inner Join product_id: 153 ms
```

Categoria agregada:

```text
Join: 6.4% do Time Spent
```

## Diagnóstico

Apesar do grande volume de registros processados pelos joins, eles não aparecem como principal gargalo temporal da execução.

O Spark/Databricks escolheu Broadcast Hash Join para ambos os casos.

Assim, os joins devem ser classificados como:

**custo presente, mas não gargalo principal nesta execução.**

# Experimento C - Análise de Rows

## Evidência observada

No Query Profile - Rows:

```text
Join (2):                 63.3%

Shuffle (3):               2.5%
Grouping Aggregate (2):    0.0%
Result Query Stage (1):     0.0%
```

Principais operadores:

```text
Inner Join customer_id     10.56 M

Scan lab30_orders          10.56 M
Shuffle customers          800 K
Scan lab30_customers       800 K
Shuffle products           50 K
Scan lab30_products        50 K
```

## Diagnóstico

A visualização Rows mostra volume processado, não tempo.

Por isso, o fato de `Join (2)` representar 63.3% das linhas não significa que os joins consumiram 63.3% do tempo.

Essa distinção foi essencial para evitar uma interpretação incorreta do Query Profile.

# Experimento D - Análise de Time Spent

## Evidência observada

No Query Profile - Time Spent:

```text
Scan (3):                 87.6%
Join (2):                  6.4%
Grouping Aggregate (2):    2.8%
Write Into (1):            2.4%
Shuffle (3):               0.9%
```

Tempos individuais observados:

```text
Scan products:     6.10 s
Scan customers:    2.95 s
Scan orders:       1.63 s

Join customer_id:  622 ms
Grouping Aggregate:338 ms
Write Into:        292 ms
Join product_id:   153 ms

Shuffle customers: 69 ms
Shuffle products:  33 ms
Shuffle aggregate: 11 ms
```

## Diagnóstico

O principal custo temporal da execução está associado às operações de Scan.

A categoria Scan respondeu por:

```text
87.6% do Time Spent
```

Esse é o principal gargalo observado neste laboratório.

Entretanto, os dados disponíveis não permitem afirmar a causa exata desse custo.

O laboratório não conclui, por exemplo, que o problema seja necessariamente:

- small files;
- cold start;
- layout físico;
- armazenamento;
- quantidade de arquivos;
- ausência de clustering.

Essas hipóteses podem ser investigadas no Lab 32.

# Experimento E - Análise de Memory Peak

## Evidência observada

No Query Profile - Memory Peak:

```text
Shuffle (3):              87.2%
Scan (3):                  9.8%
Join (2):                  1.4%
Grouping Aggregate (2):    0.9%
Write Into (1):            0.8%
```

Picos de memória observados:

```text
Shuffle aggregate: 1.18 GB
Shuffle customers: 1.17 GB
Shuffle products:  1.16 GB

Scan orders:       148.06 MB
Scan customers:    128.02 MB
Scan products:     128.01 MB

Join customer_id:   50 MB
Grouping Aggregate: 33 MB
Write Into:          32.40 MB
Join product_id:      7 MB
Grouping final:       2.13 MB
```

## Diagnóstico

O Shuffle não apresentou grande impacto temporal, mas concentrou a maior parte do pico de memória.

Assim:

```text
Shuffle:
0.9% do Time Spent
87.2% do Memory Peak
```

Esse resultado mostra que tempo de execução e consumo de memória representam perspectivas diferentes da mesma execução.

Um operador pode não ser um gargalo temporal e ainda assim representar pressão relevante de recursos.

```text
      ↓

      ↓
```

O plano físico mostra funções parciais antes do Shuffle:


e funções de consolidação depois:

```text

```

```text

```

## Diagnóstico

A agregação reduziu fortemente o volume intermediário antes do resultado final.

Ela não apareceu como gargalo principal nesta execução.

# Experimento G - Data Skew

## Evidência observada

O dataset do Lab 30 contém skew proposital em `customer_id`.

Entretanto, nesta execução foram observados:

- Broadcast Hash Join;
- baixo tempo relativo dos joins;
- baixo custo temporal de Shuffle;
- ausência, nas evidências analisadas, de partições explicitamente identificadas como stragglers.

## Diagnóstico

O skew existe nos dados do experimento, mas não foi comprovado como gargalo relevante nesta execução.

Portanto, não é correto concluir apenas pela presença de skew na geração dos dados que ele causou degradação perceptível na pipeline observada.

# Evidências Oficiais x Evidências do Laboratório

## Documentado oficialmente

As ferramentas de análise permitem observar diferentes aspectos da execução, como:

- plano lógico;
- plano físico;
- operadores;
- quantidade de linhas;
- tempo associado;
- pico de memória.

Shuffle representa redistribuição dos dados e pode ser custoso em ambientes distribuídos.

Broadcast Hash Join é uma estratégia de join utilizada quando um dos lados pode ser distribuído aos executores.

## Observado neste laboratório

Foram observados:

```text
Baseline: 7.441 s
Resultado final: 70 linhas

Scan: 87.6% do Time Spent
Join: 6.4%
Grouping Aggregate: 2.8%
Write: 2.4%
Shuffle: 0.9%

Shuffle: 87.2% do Memory Peak
```

Também foram observados:

- dois `PhotonBroadcastHashJoin`;
- filtros antecipados pelo plano otimizado;
- redução de colunas no plano;
- 10.56 milhões de linhas chegando aos joins;
- 560 resultados intermediários na agregação;
- 70 resultados finais.

## Interpretação baseada nas evidências

O principal ponto para investigação no Lab 32 é o custo dos Scans.

O Shuffle merece atenção pelo pico de memória, mas não aparece como gargalo temporal nesta execução.

Os joins, apesar do grande volume processado, não aparecem como problema dominante.

O skew foi propositalmente introduzido, mas não foi comprovado como gargalo.

---

# Conclusão

O Lab 31 mostrou que o diagnóstico de performance não deve ser feito apenas pela aparência do código.

A pipeline do Lab 30 foi construída com vários pontos potencialmente problemáticos, mas o plano de execução mostrou que o Spark/Databricks já mitigou parte deles por meio de otimizações no plano e da escolha de Broadcast Hash Join.

O Query Profile revelou que o maior custo temporal da execução esteve nos operadores de Scan, responsáveis por 87.6% do Time Spent.

Por outro lado, os operadores de Shuffle representaram apenas 0.9% do tempo, mas concentraram 87.2% do pico de memória.

Essa diferença demonstrou que tempo e memória precisam ser analisados separadamente.

Também foi possível concluir que:

- joins não foram o principal gargalo;
- agregação apresentou baixo impacto;
- Shuffle não foi gargalo temporal;
- Scan foi o principal custo observado;
- skew não foi comprovado como problema relevante;
- o otimizador já alterou significativamente a execução em relação à ordem escrita no código.

O principal aprendizado do Lab 31 é:

> **Performance Engineering não consiste em otimizar aquilo que parece ruim no código, mas em utilizar evidências da execução real para identificar onde os recursos estão sendo consumidos e decidir onde uma intervenção realmente faz sentido.**
