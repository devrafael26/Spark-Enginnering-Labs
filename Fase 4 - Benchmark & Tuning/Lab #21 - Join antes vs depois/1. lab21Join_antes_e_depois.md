## *Spark Engineering Lab 21 - Join Tuning: Antes vs Depois*

## Categoria

Benchmark & Tuning

---

## Objetivo

Avaliar o impacto de diferentes estratégias físicas de `JOIN` sobre a execução de uma mesma regra de negócio.

O laboratório compara três cenários:

1. uma **baseline automática**, na qual o Spark escolhe livremente a estratégia de join;
2. uma execução com `MERGE` explícito, orientando o Spark para um `SortMergeJoin`;
3. uma execução com `BROADCAST` explícito, orientando o Spark para um `BroadcastHashJoin`.

Além da comparação de tempo, o laboratório utiliza o plano físico e as estatísticas do otimizador para compreender **por que as estratégias possuem comportamentos diferentes**.

---

## Perguntas

* Qual estratégia de join o Spark escolhe automaticamente quando nenhuma estratégia é explicitamente informada?
* Qual é o impacto de forçar um `SortMergeJoin`?
* Qual é o impacto de informar explicitamente que o lado menor deve utilizar Broadcast?
* O Broadcast explícito apresenta vantagem consistente sobre o Broadcast escolhido automaticamente pelo Spark?
* Como o plano físico permite identificar as diferenças entre as estratégias?
* Quais informações o `explain(mode="cost")` fornece para a análise do join?
* Uma única execução é suficiente para concluir que uma estratégia é mais rápida?

---

# Cenário

Foi criado um cenário de join entre uma tabela fato significativamente maior e uma dimensão menor.

```text
df_orders
20.000.000 registros
≈ 610,4 MiB
        │
        │ product_id
        ▼
       JOIN
        ▲
        │ product_id
df_products
100.000 registros
≈ 3,1 MiB
```

A regra de negócio permanece exatamente a mesma em todos os experimentos.

Somente a estratégia utilizada para executar o join é alterada.

---

## Dados

### `df_orders`

DataFrame representando pedidos:

* `20.000.000` registros;
* `order_id`;
* `product_id`;
* `quantity`.

### `df_products`

DataFrame representando produtos:

* `100.000` registros;
* `product_id`;
* `category_id`;
* `price`.

---

## Código - Criação dos dados

```python
from pyspark.sql import functions as F
from time import perf_counter


# Fato: 20 milhões de registros
df_orders = (
    spark.range(20_000_000)
    .select(
        F.col("id").alias("order_id"),
        (F.col("id") % 100_000).alias("product_id"),
        ((F.col("id") % 5) + 1).alias("quantity")
    )
)


# Dimensão: 100 mil produtos
df_products = (
    spark.range(100_000)
    .select(
        F.col("id").alias("product_id"),
        (F.col("id") % 100).alias("category_id"),
        ((F.col("id") % 500) + 10).cast("double").alias("price")
    )
)
```

# Experimento A - Baseline automática

## Objetivo

Observar qual estratégia física o Spark escolhe quando nenhuma estratégia de join é explicitamente informada.

Nenhum hint é utilizado.

---

## Transformação

```python
df_join_baseline = (
    df_orders
    .join(
        df_products,
        on="product_id",
        how="inner"
    )
)
```

---

## Comando de análise

```python
df_join_baseline.explain(True)
```

---

## Resultado observado no plano físico

O Spark selecionou automaticamente:

```text
PhotonBroadcastHashJoin
```

Portanto, mesmo sem `F.broadcast()` ou qualquer outro hint explícito, o Spark identificou uma estratégia baseada em Broadcast para executar o join.

---

## Action

A Action utilizada para materializar a execução foi:



---

# Experimento C - Broadcast Join explícito

## Objetivo

Orientar explicitamente o Spark para utilizar `df_products` como lado Broadcast do join.

---

## Transformação

```python
df_join_broadcast = (
    df_orders
    .join(
        F.broadcast(df_products),
        on="product_id",
        how="inner"
    )
)
```

O Broadcast foi aplicado sobre:

```python
df_products
```

que representa o lado significativamente menor do join.

---

## Comandos de análise

```python
df_join_broadcast.explain(True)
```

```python
df_join_broadcast.explain(mode="cost")
```

---

## Resultado observado no plano físico

O plano físico apresentou:

```text
PhotonBroadcastHashJoin
```

Também foram observados operadores relacionados à preparação e distribuição do lado Broadcast, incluindo elementos como:

```text
Executor Broadcast
Photon Shuffle Exchange
Photon Shuffle MapStage
```

No entanto, diferentemente do cenário com `SortMergeJoin`, não foi observada a redistribuição dos **dois lados do join por `product_id`** através de:

```text
hashpartitioning(product_id, ...)
```

O lado pequeno foi preparado para Broadcast, permitindo que o lado grande fosse processado sem a necessidade do mesmo particionamento por chave exigido pelo `SortMergeJoin`.

---

## Action


---

## Interpretação do `explain(mode="cost")`

Os experimentos Merge e Broadcast utilizam exatamente os mesmos dados.

Por esse motivo, as estatísticas de entrada permanecem equivalentes:

```text
orders
≈ 610,4 MiB
20.000.000 registros

products
≈ 3,1 MiB
100.000 registros
```

A principal diferença entre os experimentos não está nos dados utilizados, mas na **estratégia física selecionada para realizar o join**.

A diferença expressiva entre os tamanhos estimados das duas relações também é compatível com a escolha automática de `df_products` como lado pequeno de um `BroadcastHashJoin`.

O `explain(mode="cost")` não representa o tempo real da execução.

Ele fornece estatísticas utilizadas no planejamento.

Assim:

```text
explain(True)
        ↓
Qual plano foi construído?

explain(mode="cost")
        ↓
Quais estatísticas estavam disponíveis
durante o planejamento?

Query Text
        ↓
Como a execução aconteceu?

perf_counter()
        ↓
Quanto tempo foi observado?
```

# Repetibilidade do benchmark

As sete execuções mostraram uma característica importante.

A baseline automática e o Broadcast explícito alternaram entre si como estratégia mais rápida:

```text
Baseline venceu:
Rodadas 1, 5 e 6

Broadcast explícito venceu:
Rodadas 2, 3, 4 e 7
```

Entretanto, os dois cenários produziram a mesma estratégia física principal:

```text
BroadcastHashJoin
```

Não foi observada, portanto, evidência suficiente para concluir que o hint explícito de Broadcast produza uma vantagem consistente sobre a decisão automática do Spark neste cenário.

Os tempos das duas estratégias permaneceram na mesma faixa geral, com variações entre as execuções.

A baseline apresentou menor dispersão durante as sete rodadas:

```text
Baseline:
0,518 s → 0,682 s
```

Enquanto o Broadcast explícito apresentou:

```text
Broadcast:
0,427 s → 1,128 s
```

Isso é uma **observação experimental**, e não permite concluir que o hint `broadcast()` seja responsável por maior variabilidade.

As diferenças entre execuções são compatíveis com variações de runtime e do ambiente de execução, porém o experimento não permite isolar a causa exata dessas variações.

# Hipótese de otimização

A hipótese inicial era que utilizar Broadcast para a relação significativamente menor poderia evitar parte do custo de redistribuição necessário ao `SortMergeJoin`.

O experimento confirmou que as execuções baseadas em `BroadcastHashJoin` apresentaram desempenho significativamente melhor que o `SortMergeJoin`.

Entretanto, também mostrou que **não foi necessário fornecer explicitamente um hint de Broadcast**, pois o Spark já selecionou automaticamente essa estratégia na baseline.

# O que foi documentado oficialmente

A documentação oficial da Databricks estabelece que:

* join hints permitem sugerir estratégias específicas ao otimizador;
* `BROADCAST` sugere uma estratégia de Broadcast Join;
* o lado que recebe o hint `BROADCAST` é o candidato a ser transmitido;
* `MERGE` sugere uma estratégia de **Shuffle Sort Merge Join**;
* quando diferentes hints são utilizados, `BROADCAST` possui prioridade sobre `MERGE`;
* uma estratégia sugerida por hint não é obrigatoriamente aplicável a todos os tipos de join.

Documentação oficial:

**Databricks - Hints**

A função PySpark:

```python
F.broadcast(df)
```

marca explicitamente um DataFrame como adequado para utilização em Broadcast Join.

Documentação oficial:

**Databricks - pyspark.sql.functions.broadcast**

A documentação da Databricks também estabelece que o **Adaptive Query Execution - AQE** pode realizar reotimizações durante a execução utilizando estatísticas de runtime e, entre outras capacidades, pode alterar dinamicamente um Sort Merge Join para Broadcast Hash Join.

Documentação oficial:

**Databricks - Adaptive Query Execution**

# O que foi observado no laboratório

Neste ambiente e com estes dados:

* `df_orders` possui `20.000.000` registros;
* `df_products` possui `100.000` registros;
* todos os joins retornaram os mesmos `20.000.000` registros;
* a baseline sem hint resultou em `PhotonBroadcastHashJoin`;
* o hint `MERGE` resultou em `SortMergeJoin`;
* o Broadcast explícito resultou em `PhotonBroadcastHashJoin`;
* o `explain(mode="cost")` apresentou aproximadamente `610,4 MiB` para `df_orders`;
* o `explain(mode="cost")` apresentou aproximadamente `3,1 MiB` para `df_products`;
* `rowCount=2.00E+7` representou os `20.000.000` registros de `df_orders`;
* `rowCount=1.00E+5` representou os `100.000` registros de `df_products`;
* em sete execuções, o Merge Join apresentou mediana de `1,277 s`;
* a baseline apresentou mediana de `0,570 s`;
* o Broadcast explícito apresentou mediana de `0,541 s`;
* baseline e Broadcast explícito alternaram entre si como execução mais rápida;
* o `SortMergeJoin` permaneceu consistentemente mais lento que os dois cenários baseados em `BroadcastHashJoin`.

# Interpretação baseada nas evidências

A diferença de tamanho entre as relações:

```text
610,4 MiB
vs
3,1 MiB
```

é compatível com a decisão do Spark de utilizar a relação `df_products` como lado pequeno do Broadcast Join.

No cenário estudado, a decisão automática do Spark foi adequada: sem intervenção explícita, o otimizador selecionou a mesma estratégia física principal utilizada no experimento com `F.broadcast()`.

O hint de Broadcast não apresentou ganho consistente sobre a baseline porque ambos os cenários terminaram utilizando:

```text
BroadcastHashJoin
```

Já ao forçar `MERGE`, houve uma mudança estrutural no plano:

```text
BroadcastHashJoin
        ↓
     versus
        ↓
SortMergeJoin
```

Essa mudança esteve associada a tempos de execução significativamente maiores durante as sete rodadas.

# Conclusão

O Lab 21 demonstrou que tuning de joins não significa simplesmente aplicar hints ou escolher manualmente uma estratégia considerada mais rápida.

O processo adequado começa pela criação de uma **baseline**, seguida da análise do plano físico, das estatísticas disponíveis ao otimizador e das métricas reais de execução.

Neste cenário, o Spark selecionou automaticamente `BroadcastHashJoin` ao unir uma relação de aproximadamente `610,4 MiB` com uma relação de aproximadamente `3,1 MiB`.

Quando o Broadcast foi explicitamente informado através de `F.broadcast()`, a estratégia física permaneceu `BroadcastHashJoin` e não foi observada vantagem consistente sobre a baseline automática.

Quando o `SortMergeJoin` foi explicitamente solicitado através do hint `MERGE`, a execução passou a envolver redistribuição e ordenação por chave e apresentou desempenho consistentemente inferior.

As sete rodadas também demonstraram que **uma única medição não é suficiente para concluir qual estratégia é superior**. Os tempos absolutos variaram entre execuções, enquanto o comportamento do plano físico permaneceu mais consistente.

O principal aprendizado do laboratório foi:

> **Tuning não significa necessariamente interferir no Spark. O diagnóstico pode demonstrar que a estratégia escolhida automaticamente pelo otimizador já é adequada.**

Além disso:

> **Uma conclusão de performance deve combinar plano físico, estatísticas, métricas de execução e repetibilidade do benchmark, e não apenas o menor tempo observado em uma única execução.**
