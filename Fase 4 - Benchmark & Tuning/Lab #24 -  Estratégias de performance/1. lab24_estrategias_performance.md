## Spark Engineering Lab 24 — Estratégias de Performance

## Categoria

Benchmark & Tuning

---

## Objetivo

Avaliar estratégias de performance sobre um mesmo workload Spark, utilizando o plano lógico otimizado, o plano físico, o Query Profile e benchmarks repetidos para distinguir:

- otimizações já realizadas automaticamente pelo Spark;
- intervenções manuais que realmente alteram o plano;
- melhorias locais em um operador que não necessariamente melhoram o workload como um todo;
- e diferenças de tempo que podem decorrer apenas de variabilidade de execução.

O laboratório também busca consolidar uma forma de raciocínio de performance engineering:

```text
Workload
   ↓
Diagnóstico
   ↓
Hipótese
   ↓
Estratégia
   ↓
Medição
   ↓
Conclusão baseada em evidências
```

---

## Perguntas

1. Escrever um filtro antes do `JOIN` melhora a performance quando o Catalyst já consegue reorganizar essa operação?
2. O plano otimizado pode ser diferente da ordem em que as transformações foram escritas?
3. Uma pré-agregação antes do `JOIN` pode reduzir o volume processado pelo operador de Join?
4. O custo adicional de uma pré-agregação e de seu Shuffle compensa a redução de linhas que chegam ao `JOIN`?
5. É possível melhorar um operador específico e, ainda assim, piorar o tempo total da query?
6. Qual estratégia apresentou melhor resultado neste workload específico?

# Dados

Foram utilizados dados artificiais gerados com `spark.range()`.

## Orders

```python
from pyspark.sql import functions as F

df_orders = (
    spark.range(30_000_000)
    .withColumn(
        "product_id",
        (F.col("id") % 1_000_000).cast("long")
    )
    .withColumn(
        "amount",
        (F.col("id") % 500) + 1
    )
)
```

Características:

- **30.000.000** de registros;
- `product_id` assume **1.000.000** de valores distintos;
- cada `product_id` aparece repetidamente ao longo de `orders`;
- `amount` varia de 1 a 500;
- o `Range` foi observado com `splits=8`.

## Products

```python
df_products = (
    spark.range(1_000_000)
    .withColumnRenamed("id", "product_id")
    .withColumn(
        "category_id",
        (F.col("product_id") % 100).cast("long")
    )
)
```

Características:

- **1.000.000** de registros;
- uma linha por `product_id`;
- `category_id` possui 100 valores possíveis;
- o `Range` também foi observado com `splits=8`.

# Experimento A — Baseline: JOIN antes do filtro

## Objetivo

Criar uma situação em que o código fosse escrito de forma aparentemente menos eficiente:

```text
JOIN
 ↓
FILTER
```

A intenção era verificar se o Spark executaria literalmente nessa ordem ou se o Catalyst reorganizaria a consulta.

## Código

```python
df_baseline = (
    df_orders
    .join(
        df_products,
        on="product_id",
        how="inner"
    )
    .filter(
        F.col("amount") >= 450
    )
    .groupBy("category_id")
    .agg(
        F.sum("amount").alias("total_amount"),
        F.count("*").alias("total_orders")
    )
)
```

## Hipótese inicial

Como o filtro `amount >= 450` elimina grande parte dos 30 milhões de registros, aplicar esse filtro somente depois do `JOIN` poderia fazer o Join trabalhar com um volume maior do que o necessário.

---

# Experimento B — Filtro antes do JOIN

## Objetivo

Aplicar manualmente uma estratégia clássica de redução antecipada de dados:

```text
FILTER
 ↓
JOIN
```

## Código

```python
df_orders_filtered = (
    df_orders
    .filter(
        F.col("amount") >= 450
    )
)

df_optimized = (
    df_orders_filtered
    .join(
        df_products,
        on="product_id",
        how="inner"
    )
    .groupBy("category_id")
    .agg(
        F.sum("amount").alias("total_amount"),
        F.count("*").alias("total_orders")
    )
)
```

---

# Resultado dos Experimentos A e B

## Parsed / Analyzed Logical Plan

No Experimento A, a ordem escrita aparecia como:

```text
Join
 ↓
Filter
```

## Optimized Logical Plan

O Catalyst reorganizou o plano para:

```text
Range
 ↓
Filter
 ↓
Project
 ↓
Join
```

Ou seja, mesmo no Experimento A, o filtro passou a ser aplicado antes do Join no plano otimizado.

O Experimento B já havia sido escrito dessa forma.

Como consequência, os dois experimentos convergiram para planos otimizados e físicos essencialmente equivalentes.

## Physical Plan observado

Nos dois casos foram observados, entre outros:

```text

 ↓

 ↓

 ↓
PhotonShuffleExchange

PhotonGroupingAgg
```

Também foi observado:

```text

```

e:


## Query Profile

O Query Profile confirmou que o filtro foi aplicado antes do Join e reduziu o volume de `orders` de aproximadamente:

```text

     ↓
~3.060.000
```

antes do operador de Join.

Portanto, a intervenção manual do Experimento B não criou uma estratégia física nova: o Catalyst já havia realizado essa otimização no Experimento A.

# Experimento D — Pré-agregação antes do JOIN

## Objetivo

Testar uma estratégia real de redução de cardinalidade antes do Join.

Como existem apenas 1 milhão de `product_id` distintos nos 30 milhões de registros de `orders`, a pré-agregação poderia reduzir:

```text
30M
 ↓
1M
```

antes do Join.

## Código

```python
df_orders_agg = (
    df_orders
    .groupBy("product_id")
    .agg(
        F.sum("amount").alias("product_total_amount"),
        F.count("*").alias("product_total_orders")
    )
)

df_experimento_d = (
    df_orders_agg
    .join(
        df_products,
        on="product_id",
        how="inner"
    )
    .groupBy("category_id")
    .agg(
        F.sum("product_total_amount").alias("total_amount"),
        F.sum("product_total_orders").alias("total_orders")
    )
)
```

## Fluxo conceitual

```text
orders: 30M
     ↓
GROUP BY product_id
     ↓
~1M
     +
products: 1M
     ↓
JOIN
     ↓
GROUP BY category_id
     ↓
resultado
```

# Observação importante sobre Time Spent e Wall-clock

Os tempos associados aos operadores no Query Profile não devem ser simplesmente somados para reproduzir o wall-clock total.

`Time Spent` pode representar trabalho acumulado de operadores executados de forma distribuída e paralela.

Já o wall-clock representa o tempo decorrido de ponta a ponta da query.

Portanto:

```text
tempo dos operadores somados
≠
necessariamente wall-clock total
```

# O que foi documentado oficialmente

## Performance tuning no Spark SQL

A documentação oficial do Apache Spark apresenta diferentes mecanismos de tuning, incluindo:

- cache;
- tuning de partições;
- estatísticas;
- estratégias de Join;
- AQE.

Também documenta que `spark.sql.shuffle.partitions` controla o número de partições utilizadas em Shuffles de operações como joins e agregações.

Documentação oficial:

https://spark.apache.org/docs/latest/sql-performance-tuning.html

## Shuffle

A documentação de tuning do Apache Spark descreve operações como `join`, `groupByKey`, `reduceByKey` e outras como operações que podem gerar Shuffle e demandar estruturas intermediárias significativas durante o processamento distribuído.

Documentação oficial:

https://spark.apache.org/docs/latest/tuning.html

## AQE

A documentação oficial do Spark estabelece que o Adaptive Query Execution utiliza estatísticas de runtime para reotimizar o plano durante a execução.

Entre suas capacidades documentadas estão:

- coalescer partições pós-Shuffle;
- tratar skew;
- alterar certas estratégias de Join em runtime.

Documentação oficial:

https://spark.apache.org/docs/latest/sql-performance-tuning.html#adaptive-query-execution

# O que foi observado nos experimentos

## A vs B

Foi observado que:

- o código A foi escrito como `JOIN → FILTER`;
- no Optimized Logical Plan, o filtro foi movido para antes do Join;
- o plano físico de A e B tornou-se essencialmente equivalente;
- o Query Profile confirmou a redução do lado de `orders` antes do Join;
- sete rodadas não demonstraram vantagem consistente da intervenção manual.

## C vs D

Foi observado que:

- C levou os 30 milhões de registros de `orders` para a estratégia de Join antes da agregação por categoria;
- D realizou uma pré-agregação por `product_id`;
- D reduziu o volume do lado de `orders` para aproximadamente 1 milhão de grupos antes do Join;
- o Join caiu de **883 ms** em C para **476 ms** em D;
- porém D introduziu um Shuffle por `product_id` de **3,80 s**;
- o gargalo migrou do Join para o Shuffle/pré-agregação;
- C venceu todas as sete rodadas válidas do benchmark.

# Interpretação baseada nas evidências

## 1. Nem toda otimização manual é necessária

A comparação A vs B mostrou que uma transformação aparentemente melhor escrita pelo desenvolvedor pode já ser realizada automaticamente pelo Catalyst.

Portanto:

```text
não basta analisar apenas a ordem escrita no código
```

É necessário observar:

```text
Optimized Logical Plan
Physical Plan
Query Profile
```

antes de concluir que existe uma oportunidade real de tuning.

## 2. Reduzir linhas antes do Join não é suficiente para garantir melhor performance

O Experimento D reduziu drasticamente a cardinalidade antes do Join:

```text
30M → ~1M
```

e o próprio Join ficou significativamente mais barato.

Mesmo assim, o workload completo ficou mais lento.

A razão observada foi o custo adicional criado pela pré-agregação, principalmente o Shuffle por `product_id`.

## 3. Otimizar um operador não significa otimizar o workload

No D:

```text
Join ficou melhor
```

mas:

```text
query inteira ficou pior
```

Logo, performance deve ser avaliada pelo custo total do plano, e não apenas pelo desempenho isolado de um operador.

## 4. Join e Shuffle não são custos concorrentes independentes

Não existe uma regra universal como:

```text
Shuffle é sempre mais caro que Join
```

ou:

```text
Join é sempre mais caro que Shuffle
```

Muitos joins distribuídos utilizam Shuffle como parte de sua própria estratégia física.

O custo depende de fatores como:

- volume de dados;
- tamanho em bytes das linhas;
- cardinalidade;
- distribuição das chaves;
- skew;
- número e tamanho das partições;
- estratégia física escolhida;
- recursos disponíveis;
- otimizações do Catalyst, AQE e Photon;
- custo introduzido pela alternativa de tuning.

## 5. A melhor estratégia é workload-dependent

Neste laboratório:

```text
Experimento C
JOIN antes da agregação
```

foi a melhor estratégia global.

Porém, esse resultado não deve ser generalizado como regra.

Em outro cenário, por exemplo:

```text
bilhões de linhas
 ↓
pré-agregação
 ↓
fortíssima redução de cardinalidade
```

o custo da pré-agregação poderia ser compensado pelo volume economizado nas operações seguintes.

A decisão deve ser baseada em evidências do workload real.

# Conclusão

O Lab 24 demonstrou que performance engineering em Spark não consiste em aplicar automaticamente técnicas conhecidas, mas em diagnosticar o plano, formular hipóteses e validar o impacto das intervenções.

No primeiro conjunto de experimentos, A e B, foi testada a hipótese de que aplicar manualmente um filtro antes do Join melhoraria a execução. O Catalyst, entretanto, já havia realizado essa reorganização no baseline. Como resultado, os planos tornaram-se essencialmente equivalentes e o benchmark não apresentou vantagem consistente da intervenção manual.

No segundo conjunto, C e D, foi testada uma intervenção que realmente alterou o workload. A pré-agregação reduziu `orders` de 30 milhões para aproximadamente 1 milhão de registros antes do Join e reduziu o custo do próprio Join de 883 ms para 476 ms. Entretanto, essa redução exigiu uma agregação e um Shuffle adicionais, sendo observado um Shuffle por `product_id` de 3,80 s.

O resultado global foi consistente: o Experimento C venceu as sete rodadas válidas do benchmark, com média aproximada de 1,097 s contra 1,578 s do Experimento D.

Portanto, neste workload e neste ambiente:

> **manter o Join antes da pré-agregação foi a estratégia mais eficiente globalmente.**

A principal conclusão do laboratório é:

> **Não se deve minimizar o número de linhas de um operador a qualquer custo. O objetivo é minimizar o custo total do plano.**

Uma otimização pode tornar um operador específico mais barato e, ainda assim, tornar a query inteira mais lenta.

O processo adequado é:

```text
medir
 ↓
identificar o gargalo
 ↓
formular uma hipótese
 ↓
aplicar uma estratégia
 ↓
comparar os planos e métricas
 ↓
validar se o workload completo realmente melhorou
```

Esse resultado encerra a Fase 4 — Benchmark & Tuning consolidando o raciocínio de performance engineering desenvolvido ao longo dos Labs anteriores.
