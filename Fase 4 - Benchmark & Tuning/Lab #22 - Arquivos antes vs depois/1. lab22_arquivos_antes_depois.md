## *Spark Engineering Lab 22 - Arquivos: antes vs depois*

## Categoria

Performance Engineering / Benchmark & Tuning

---

## Objetivo

Avaliar como a organização física de uma tabela Delta em arquivos pode influenciar sua leitura e comparar o comportamento da tabela antes e depois de uma operação de compactação com `OPTIMIZE`.

O laboratório buscou criar propositalmente um cenário com vários arquivos pequenos, medir esse estado inicial, executar a compactação e então repetir a mesma consulta para comparar:

- quantidade de arquivos físicos;
- tamanho do snapshot da tabela;
- arquivos efetivamente lidos pela consulta;
- volume lido;
- tempo das execuções;
- comportamento apresentado no Query Profile.

---

## Pergunta

Como a quantidade e o tamanho dos arquivos que compõem uma tabela Delta influenciam a leitura e o que muda após a compactação com `OPTIMIZE`?

---

## Conceito principal

Uma tabela Spark/Delta não deve ser observada apenas do ponto de vista lógico, como linhas e colunas.

No armazenamento, os dados são persistidos em arquivos físicos, e a organização desses arquivos faz parte do layout físico da tabela.

Muitos arquivos pequenos podem introduzir overhead durante a leitura, pois o mecanismo de execução precisa lidar com uma quantidade maior de arquivos.

A Databricks documenta que leituras envolvendo muitos arquivos pequenos podem aumentar o tempo de scan e recomenda a compactação desses arquivos, inclusive através do comando `OPTIMIZE`.

Documentação oficial:

https://docs.databricks.com/aws/pt/sql/user/queries/performance-insights

https://docs.databricks.com/aws/en/delta/tutorial

---

## Distinção importante - Spark Partition ≠ arquivo físico

Neste laboratório foi importante separar dois conceitos já estudados anteriormente.

### Spark Partition

É uma divisão lógica dos dados utilizada pelo Spark durante o processamento distribuído.

### Arquivo físico

É o arquivo persistido no armazenamento quando os dados são gravados, como um arquivo Parquet pertencente a uma tabela Delta.

Portanto:

```text
Spark Partition ≠ arquivo físico
```

No experimento foi utilizado:

```python
df.repartition(100)
```

O DataFrame foi redistribuído em 100 partitions antes da escrita.

Após a gravação da tabela Delta, foram observados exatamente 100 arquivos físicos.

Neste laboratório ocorreu:

```text
100 Spark partitions para a escrita
              ↓
100 arquivos físicos observados
```

Esse resultado pertence ao experimento e não deve ser interpretado como uma regra universal de que:

```text
1 Spark partition = 1 arquivo
```

# Experimento A - Criação proposital do cenário com small files

## Dados

Foi criado um DataFrame artificial com 30 milhões de registros utilizando `spark.range()`.

As colunas auxiliares foram derivadas através de operações de módulo para gerar valores repetitivos.

```python
from pyspark.sql import functions as F

table_name = "workspace.default.lab22_files"

spark.sql(f"DROP TABLE IF EXISTS {table_name}")

df = (
    spark.range(30_000_000)
    .withColumn(
        "customer_id",
        (F.col("id") % 1_000_000).cast("long")
    )
    .withColumn(
        "category_id",
        (F.col("id") % 100).cast("int")
    )
    .withColumn(
        "amount",
        (F.col("id") % 1000).cast("double")
    )
)

print("Quantidade de linhas:")
print(df.count())
```

Resultado:

```text
30.000.000 linhas
```

---

## Transformações

Para produzir propositalmente várias partitions antes da escrita:

```python
df_files = df.repartition(100)
```

O objetivo foi criar um estado inicial artificial com muitos arquivos pequenos para posteriormente comparar com o resultado da compactação.

---

## Action

Os dados foram persistidos como uma tabela Delta:

```python
(
    df_files
    .write
    .format("delta")
    .mode("overwrite")
    .saveAsTable(table_name)
)
```

---

## Comando de análise

O estado físico inicial da tabela foi observado utilizando:

```python
detail_before = spark.sql("""
    DESCRIBE DETAIL workspace.default.lab22_files
""")

display(
    detail_before.select(
        "format",
        "numFiles",
        "sizeInBytes"
    )
)
```

Também foi calculado o tamanho médio aproximado dos arquivos:

```python
row = detail_before.select(
    "numFiles",
    "sizeInBytes"
).first()

num_files_before = row["numFiles"]
size_bytes_before = row["sizeInBytes"]

print(f"Número de arquivos: {num_files_before}")
print(f"Tamanho total: {size_bytes_before:,} bytes")
print(f"Tamanho total: {size_bytes_before / (1024**2):.2f} MB")

if num_files_before > 0:
    avg_file_mb = (
        size_bytes_before / num_files_before / (1024**2)
    )

    print(
        f"Tamanho médio aproximado por arquivo: "
        f"{avg_file_mb:.2f} MB"
    )
```

---

## Resultado observado - estado inicial

```text
Linhas:                         30.000.000
Número de arquivos:            100
Tamanho total:                 24.764.811 bytes
Tamanho total aproximado:      23,62 MB
Tamanho médio por arquivo:     ~0,24 MB
```

Foi produzido, portanto, um cenário intencional de vários arquivos pequenos.

# Experimento B - Benchmark antes do OPTIMIZE

## Consulta

Foi utilizada uma agregação sobre toda a tabela:

```sql
SELECT
    category_id,
    SUM(amount) AS total_amount,
    COUNT(*) AS total_rows
FROM workspace.default.lab22_files
GROUP BY category_id
```

O objetivo era manter exatamente a mesma consulta antes e depois da compactação.

---

## Benchmark

Foram realizadas três execuções:

```python
import time

query = """
SELECT
    category_id,
    SUM(amount) AS total_amount,
    COUNT(*) AS total_rows
FROM workspace.default.lab22_files
GROUP BY category_id
"""

for rodada in range(1, 4):

    inicio = time.perf_counter()

    spark.sql(query).collect()

    fim = time.perf_counter()

    print(f"Rodada {rodada}: {fim - inicio:.3f} s")
```

Resultados:

```text
Rodada 1: 10,149 s
Rodada 2:  1,373 s
Rodada 3:  1,450 s
```

---

## Query Profile - antes

A consulta também foi executada através de `display()` para análise do Query Profile:

```python
result_before = spark.sql("""
SELECT
    category_id,
    SUM(amount) AS total_amount,
    COUNT(*) AS total_rows
FROM workspace.default.lab22_files
GROUP BY category_id
""")

display(result_before)
```

### Métricas observadas

```text

Bytes read:                23,62 MB
Bytes pruned:              0 bytes
Bytes read from cache:     100%

Files read:                100
Files pruned:              0

Grouping Aggregate:        281 ms
Shuffle:                   4 ms

Aggregated task time:      650 ms
Tasks time in Photon:      79%
```

---

## Observação sobre a primeira rodada

A primeira execução apresentou:

```text
10,149 s
```

enquanto as duas seguintes ficaram próximas de:

```text
1,4 s
```

Essa diferença é compatível com efeitos de aquecimento do ambiente, inicialização e cache.

A própria execução analisada no Query Profile mostrou:

```text
Bytes read from cache = 100%
```

Portanto, as rodadas posteriores estavam sendo realizadas em uma condição diferente da primeira execução.

Para evitar uma comparação incorreta, a primeira rodada não foi utilizada como principal referência na comparação de desempenho antes/depois.

Documentação oficial relacionada ao cache:

# Experimento C - Compactação com OPTIMIZE

## Action

Foi executado:

```python
optimize_result = spark.sql("""
OPTIMIZE workspace.default.lab22_files
""")

display(optimize_result)
```

O `OPTIMIZE` reescreveu os arquivos da tabela.

Para tabelas Delta sem Liquid Clustering e sem uma cláusula de colocação específica, a Databricks documenta que o `OPTIMIZE` realiza uma otimização por bin-packing.

O objetivo é produzir arquivos mais equilibrados em relação ao tamanho físico no armazenamento.

Documentação oficial:

https://docs.databricks.com/aws/en/sql/language-manual/delta-optimize

https://docs.databricks.com/aws/en/delta/optimize

---

## Estado da tabela depois do OPTIMIZE

Foi executado novamente:

```python
detail_after = spark.sql("""
DESCRIBE DETAIL workspace.default.lab22_files
""")
```

Resultado:

```text
Número de arquivos:        1
sizeInBytes:               696.362 bytes
Tamanho aproximado:        0,66 MB
Tamanho médio por arquivo: 0,66 MB
```

A quantidade de registros também foi validada:

```python
spark.sql("""
SELECT COUNT(*) AS total_rows
FROM workspace.default.lab22_files
""").show()
```

Resultado:

```text
30.000.000 linhas
```

Portanto:

```text
ANTES

30.000.000 linhas
100 arquivos

        ↓

OPTIMIZE

        ↓

DEPOIS

30.000.000 linhas
1 arquivo
```

A organização física dos dados mudou, enquanto o conteúdo lógico permaneceu o mesmo.

A Databricks documenta que `OPTIMIZE` não altera os dados lógicos da tabela, portanto leituras antes e depois da operação devem retornar os mesmos resultados.

Documentação oficial:

https://docs.databricks.com/aws/en/delta/optimize

# Experimento D - Benchmark depois do OPTIMIZE

## Consulta

Foi executada exatamente a mesma consulta utilizada no cenário anterior:

```python
result_after = spark.sql("""
SELECT
    category_id,
    SUM(amount) AS total_amount,
    COUNT(*) AS total_rows
FROM workspace.default.lab22_files
GROUP BY category_id
""")

display(result_after)
```

---

## Query Profile - depois

Foram observadas as seguintes métricas:

```text
Rows returned:             100
Rows read:                 30.000.000
Bytes read:                256 KB
Bytes pruned:              0 bytes
Bytes read from cache:     0%

Files read:                1
Files pruned:              0

Scan Table:                475 ms
Grouping Aggregate:        202 ms

Aggregated task time:      686 ms
Tasks time in Photon:      99%
```

A evidência principal foi:

```text
Files read

ANTES:  100
DEPOIS:   1
```

A consulta continuou processando:

```text
30.000.000 linhas
```

mas passou a acessar apenas um arquivo físico.

---

## Observação - Bytes lidos

Antes:

```text
Bytes read = 23,62 MB
```

Depois:

```text
Bytes read = 256 KB
```

O `DESCRIBE DETAIL`, entretanto, apresentava:

```text
sizeInBytes ≈ 0,66 MB
```

Essas métricas não representam necessariamente a mesma coisa.

`sizeInBytes` representa o tamanho físico do snapshot atual da tabela.

Já a consulta não utiliza todas as colunas existentes:

```text
id
customer_id
category_id
amount
```

A query utiliza principalmente:

```text
category_id
amount
```

Como os arquivos utilizados pelo Delta Lake são colunares, a leitura pode acessar somente as colunas necessárias à execução.

Portanto:

```text
tamanho físico do arquivo
        ≠
bytes necessariamente lidos pela query
```

---

## Observação - comparação do Scan Table

Antes:

```text
Scan Table = 227 ms
Cache = 100%
```

Depois:

```text
Scan Table = 475 ms
Cache = 0%
```

Não é correto concluir que a compactação tornou o Scan mais lento.

Os dois Query Profiles foram executados sob condições diferentes:

```text
ANTES  → dados atendidos pelo cache
DEPOIS → dados não atendidos pelo cache
```

Portanto, os valores:

```text
227 ms
vs
475 ms
```

não constituem uma comparação controlada do efeito da compactação.

Essa diferença reforça a importância de observar o contexto das métricas, e não somente o tempo individual de um operador.

---

# Benchmark depois do OPTIMIZE

As três execuções apresentaram:

```text
Rodada 1: 1,183 s
Rodada 2: 1,074 s
Rodada 3: 1,057 s
```

# Comparação do benchmark

A primeira rodada do cenário anterior foi desconsiderada da comparação principal devido ao forte efeito de warm-up observado.

Foram então comparadas as rodadas aquecidas.

## Antes

```text
Rodada 2: 1,373 s
Rodada 3: 1,450 s

Média ≈ 1,412 s
```

## Depois

```text
Rodada 2: 1,074 s
Rodada 3: 1,057 s

Média ≈ 1,066 s
```

Diferença observada:

```text
1,412 s
   ↓
1,066 s

≈ 24,5% menor
```

Portanto, nas rodadas aquecidas deste laboratório, o cenário compactado apresentou tempo médio aproximadamente 24,5% menor.

Esse valor representa somente o comportamento observado neste experimento e não deve ser interpretado como um ganho universal produzido pelo `OPTIMIZE`.

# O que está documentado oficialmente

A Databricks documenta que muitos arquivos pequenos podem aumentar o tempo de scan de uma tabela.

Documentação oficial:

https://docs.databricks.com/aws/pt/sql/user/queries/performance-insights

---

O `OPTIMIZE` pode ser utilizado para compactar arquivos pequenos e melhorar o layout físico dos dados.

Documentação oficial:

https://docs.databricks.com/aws/en/delta/optimize

---

Quando não é utilizado Liquid Clustering nem uma estratégia de colocação específica, o `OPTIMIZE` utiliza bin-packing para produzir arquivos mais equilibrados em relação ao tamanho físico no armazenamento.

Documentação oficial:

https://docs.databricks.com/aws/en/sql/language-manual/delta-optimize

---

A operação `OPTIMIZE` não altera logicamente os dados da tabela. Uma leitura realizada antes e depois da operação deve produzir os mesmos resultados.

Documentação oficial:

https://docs.databricks.com/aws/en/delta/optimize

---

A Databricks também possui mecanismos automáticos para lidar com layout e tamanho dos arquivos, como compactação automática e otimizações de escrita.

Documentação oficial:

https://docs.databricks.com/gcp/pt/lakehouse-architecture/performance-efficiency/best-practices.html

# Interpretação baseada nas evidências

O laboratório demonstrou que o layout físico dos arquivos pode ser uma dimensão relevante da performance de leitura.

Neste experimento, a compactação reduziu drasticamente a quantidade de arquivos que precisavam ser manipulados:

```text
100 → 1
```

sem alterar a quantidade lógica de dados:

```text
30.000.000 → 30.000.000
```

Também foi observado um tempo médio menor nas execuções aquecidas após a compactação.

Entretanto, o experimento também demonstrou que métricas isoladas precisam ser interpretadas cuidadosamente.

O `Scan Table`, por exemplo, apresentou:

```text
227 ms antes
475 ms depois
```

mas as condições de cache eram diferentes:

```text
ANTES  → 100% do volume lido do cache
DEPOIS → 0% do volume lido do cache
```

Portanto, essa métrica isoladamente não permite afirmar que o Scan ficou mais rápido ou mais lento devido ao `OPTIMIZE`.

# Conclusão

O Lab 22 demonstrou na prática a diferença entre o particionamento utilizado pelo Spark durante o processamento e os arquivos físicos persistidos no armazenamento.

Foi criado propositalmente um cenário de small files utilizando:

```python
repartition(100)
```

antes da escrita.

O resultado observado foi uma tabela Delta contendo:

```text
100 arquivos físicos
30.000.000 linhas
```

Após a execução de:

```sql
OPTIMIZE workspace.default.lab22_files
```

o snapshot atual passou a possuir:

```text
1 arquivo físico
30.000.000 linhas
```

Isso demonstrou que o `OPTIMIZE` reorganizou o layout físico da tabela sem alterar seu conteúdo lógico.

O Query Profile também evidenciou diretamente a mudança:

```text
Files read

100 → 1
```

Nas execuções aquecidas, o tempo médio observado caiu de aproximadamente:

```text
1,412 s
```

para:

```text
1,066 s
```

uma redução de aproximadamente 24,5% neste experimento.

O principal aprendizado do laboratório é que problemas de performance no Spark não estão relacionados apenas a joins, shuffles ou partitions de processamento.

A organização física dos dados também precisa ser considerada:

```text
Spark partitions
        ↓
influenciam a execução e a escrita

Arquivos físicos
        ↓
compõem o layout persistido da tabela

Muitos arquivos pequenos
        ↓
podem aumentar o overhead de leitura

OPTIMIZE
        ↓
compacta e reorganiza os arquivos

Benchmark
        ↓
mede se a mudança física produziu efeito na execução
```

Assim, o Lab 22 complementa o Lab 19: enquanto o Lab 19 estudou o funcionamento do `OPTIMIZE`, o Lab 22 criou deliberadamente um cenário de small files e avaliou, por meio de métricas e benchmark, o comportamento da tabela antes e depois da compactação.
