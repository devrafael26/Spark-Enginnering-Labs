## *Spark Engineering Lab 23 - Partições: antes vs depois*

## Categoria

Performance Engineering / Benchmark & Tuning

## Objetivo

Avaliar o impacto do particionamento na execução de uma agregação em Apache Spark, comparando diferentes intervenções manuais com um cenário sem `repartition()` explícito.

O laboratório busca demonstrar que alterar o número de partições não garante melhoria de performance e que uma intervenção manual pode introduzir etapas adicionais de Shuffle e aumentar o custo da execução.

---

## Pergunta

Como diferentes estratégias de particionamento afetam o desempenho de uma mesma agregação?

Uma intervenção manual com `repartition()` melhora a execução ou pode adicionar custo desnecessário?

---

## Experimento

Foi criado um único dataset com 100 milhões de registros.

A mesma transformação e a mesma Action foram mantidas em todos os cenários.

A principal variável entre os experimentos foi o particionamento:

- Experimento A: `repartition(2)`
- Experimento B: `repartition(16)`
- Experimento C: `repartition(500)`
- Experimento D: nenhuma intervenção manual com `repartition()`

A transformação utilizada consistiu em agrupar os dados por `group_id` e calcular a soma da coluna `value`.

---

## Dados

Dataset base:

```python
from pyspark.sql import functions as F

df = (
    spark.range(100_000_000)
    .withColumn("group_id", F.col("id") % 1000)
    .withColumn("value", F.col("id") * 0.01)
)
```

Características:

- 100.000.000 de registros;
- `group_id` com 1.000 valores possíveis;
- coluna `value` derivada do `id`;
- `spark.range()` apresentado no plano com `splits=8`.

---

## Transformações

A transformação principal foi mantida em todos os experimentos:

```python
result = (
    df
    .groupBy("group_id")
    .agg(
        F.sum("value").alias("total_value")
    )
)
```

Nos Experimentos A, B e C foi adicionada uma transformação anterior:

```python
df.repartition(N)
```

No Experimento D não houve intervenção manual no particionamento.

---

## Action

A Action utilizada para disparar a execução foi:

```python
result.count()
```

O resultado esperado foi de 1.000 linhas, correspondentes aos 1.000 valores possíveis de `group_id`.

---

## Comando de análise

Foram utilizados:

```python
result.explain(True)
```

e medição de tempo com:

```python
time.perf_counter()
```

Os principais elementos observados nos planos físicos foram:

- `PhotonRange`;
- `PhotonProject`;
- `PhotonGroupingAgg`;
- `PhotonShuffleExchange`;
- `RoundRobinPartitioning`;
- `hashpartitioning`;
- `AdaptiveSparkPlan`;
- `PhotonSort`.

---

# Experimento A - `repartition(2)`

## Código

```python
import time

df_a = df.repartition(2)

result_a = (
    df_a
    .groupBy("group_id")
    .agg(
        F.sum("value").alias("total_value")
    )
)

result_a.explain(True)

inicio = time.perf_counter()

rows_a = result_a.count()

tempo_a = time.perf_counter() - inicio

print("=== EXPERIMENTO A ===")
print("Partitions solicitadas: 2")
print(f"Linhas resultantes: {rows_a:,}")
print(f"Tempo: {tempo_a:.3f} s")
```

## Resultado observado

```text
Partitions solicitadas: 2
Linhas resultantes: 1,000
Tempo: 5.586 s
```

Este foi o cenário mais lento entre os quatro experimentos.

# Experimento B - `repartition(16)`

## Código

```python
df_b = df.repartition(16)

result_b = (
    df_b
    .groupBy("group_id")
    .agg(
        F.sum("value").alias("total_value")
    )
)

result_b.explain(True)

inicio = time.perf_counter()

rows_b = result_b.count()

tempo_b = time.perf_counter() - inicio

print("=== EXPERIMENTO B ===")
print("Partitions solicitadas: 16")
print(f"Linhas resultantes: {rows_b:,}")
print(f"Tempo: {tempo_b:.3f} s")
```

## Resultado observado

```text
Partitions solicitadas: 16
Linhas resultantes: 1,000
Tempo: 2.447 s
```

O aumento de 2 para 16 partições melhorou significativamente o tempo em relação ao Experimento A.

Entretanto, o plano físico mostrou que o `repartition(16)` introduziu uma etapa adicional de redistribuição.

Trecho relevante:

```text
PhotonShuffleExchangeSink RoundRobinPartitioning(16)
```

Essa etapa foi criada diretamente pelo:

```python
df.repartition(16)
```

Depois dela, a agregação ainda precisou executar outro Shuffle:

```text
PhotonShuffleExchangeSink hashpartitioning(group_id, 762)
```

Portanto, o `repartition(16)` não substituiu o Shuffle necessário ao `groupBy`.

Ele acrescentou um Shuffle anterior.

---

## Plano físico observado - Experimento B

```text
AdaptiveSparkPlan isFinalPlan=false

   PhotonResultStage
   +- PhotonColumnarToRow
```

# Comparação principal - Experimento B vs Experimento D

A comparação entre B e D permitiu identificar claramente o efeito da intervenção manual.

## Experimento B

O plano apresentou dois Shuffles:

```text
RoundRobinPartitioning(16)
```

e:

```text
hashpartitioning(group_id, 762)
```

O primeiro foi introduzido explicitamente pelo:

```python
repartition(16)
```

O segundo foi necessário para a agregação por `group_id`.

Além disso, no plano B apareceu:

```text
PhotonSort
```

antes do `RoundRobinPartitioning(16)`.

---

## Experimento D

Sem `repartition()` manual, não apareceu o:

```text
RoundRobinPartitioning(16)
```

O plano pôde executar a agregação parcial antes do Shuffle necessário ao `groupBy`:

```text
Range
  ↓
Project
  ↓
Partial SUM
  ↓
Shuffle por group_id
  ↓
Final SUM
```

Isso evitou a redistribuição adicional observada no Experimento B.

---

# Agregação parcial

Um ponto importante observado no plano foi a divisão da agregação em duas etapas:

```text
partial_sum(value)
```

e:

```text
finalmerge_sum(...)
```

No Experimento D, o Spark conseguiu executar a agregação parcial antes do Shuffle:

```text
dados
  ↓
partial_sum
  ↓
Shuffle por group_id
  ↓
finalmerge_sum
```

Isso permite reduzir os dados intermediários antes da redistribuição necessária para consolidar os grupos.

No Experimento B, o `repartition(16)` foi executado antes dessa agregação parcial:

```text
dados
  ↓
RoundRobinPartitioning(16)
  ↓
partial_sum
  ↓
Shuffle por group_id
  ↓
finalmerge_sum
```

Portanto, a intervenção manual introduziu uma redistribuição anterior à agregação parcial.

---

# Sobre as 16 e as 762 partições

O plano mostrou:

```text
RoundRobinPartitioning(16)
```

e posteriormente:

```text
hashpartitioning(group_id, 762)
```

Esses valores representam etapas diferentes do plano.

As 16 partições foram solicitadas explicitamente pelo código:

```python
df.repartition(16)
```

Já as 762 partições pertencem ao Shuffle utilizado para satisfazer os requisitos da agregação por `group_id`.

Portanto, não seria correto afirmar que o Experimento B "executou com 16 partições" durante toda a consulta.

O correto é:

> O `repartition(16)` criou uma etapa de redistribuição em 16 partições. Posteriormente, o `groupBy` realizou outro Shuffle utilizando `hashpartitioning(group_id, 762)` no plano inicial observado.

---

# AQE - Adaptive Query Execution

Nos dois planos analisados apareceu:

```text
AdaptiveSparkPlan isFinalPlan=false
```

e:

```text
== Initial Plan ==
```

Isso indica que o plano apresentado corresponde ao plano inicial de uma execução adaptativa.

A documentação oficial do Databricks estabelece que o AQE pode modificar o plano durante a execução utilizando estatísticas obtidas em runtime, incluindo a possibilidade de coalescer partições pequenas após Shuffle.

Entretanto, neste laboratório não foi possível observar um `Final Plan` que comprovasse quais adaptações foram efetivamente realizadas.

Dessa forma, não podemos afirmar que:

```text
762 partições foram reduzidas pelo AQE
```

nem que:

```text
762 partições foram mantidas até o final
```

O que pode ser afirmado é apenas que:

```text
hashpartitioning(group_id, 762)
```

foi observado no `Initial Plan`.

# O que foi documentado oficialmente

## `repartition()`

O `repartition()` redistribui os dados e pode introduzir uma operação de Exchange/Shuffle para produzir o novo particionamento.

Documentação oficial:

https://spark.apache.org/docs/latest/api/python/reference/pyspark.sql/api/pyspark.sql.DataFrame.repartition.html

---

## Shuffle partitions

Operações como agregações e joins podem exigir redistribuição dos dados entre partições.

Documentação oficial:

https://spark.apache.org/docs/latest/sql-performance-tuning.html

---

## Adaptive Query Execution

O AQE pode adaptar o plano durante a execução utilizando estatísticas em runtime.

Entre seus recursos está o coalescing de pequenas partições após Shuffle.

Documentação oficial:

https://docs.databricks.com/aws/en/optimizations/aqe

---

# O que foi observado no laboratório

Os resultados experimentais mostraram:

```text
repartition(2)   → 5.586 s
repartition(16)  → 2.447 s
repartition(500) → 4.248 s
automático       → 0.459 s
```

Foi observado que:

- poucas partições tiveram o pior resultado;
- aumentar de 2 para 16 melhorou o desempenho;
- aumentar para 500 piorou novamente;
- nenhuma intervenção manual apresentou o melhor resultado;
- `repartition(16)` adicionou um `RoundRobinPartitioning(16)`;
- o `groupBy` continuou necessitando de outro Shuffle;
- B apresentou dois Shuffles no plano inicial;
- D apresentou apenas o Shuffle necessário à agregação;
- os dois cenários apresentaram `hashpartitioning(group_id, 762)` no plano inicial;
- o plano disponível foi `isFinalPlan=false`, portanto não foi possível verificar as adaptações finais do AQE.

---

# Interpretação baseada nas evidências

Os resultados não permitem concluir que uma quantidade específica de partições, como 16, seja universalmente melhor.

O que o experimento evidencia é que alterar o particionamento sem necessidade pode adicionar trabalho ao plano físico.

No Experimento B:

```text
repartition(16)
        ↓
Shuffle adicional
        ↓
agregação parcial
        ↓
Shuffle necessário ao groupBy
```

No Experimento D:

```text
agregação parcial
        ↓
Shuffle necessário ao groupBy
```

A diferença estrutural observada no plano é compatível com o desempenho significativamente melhor do Experimento D.

Entretanto, como o plano apresentado foi apenas o `Initial Plan`, não foi possível determinar se o AQE realizou adaptações adicionais durante a execução.

---

# Conclusão

O Lab 23 demonstrou que controlar manualmente a quantidade de partições não significa automaticamente otimizar uma execução Spark.

Nos experimentos:

```text
2 partições   → 5.586 s
16 partições  → 2.447 s
500 partições → 4.248 s
automático    → 0.459 s
```

A mudança de 2 para 16 partições melhorou o desempenho, enquanto o aumento para 500 partições voltou a aumentar o tempo de execução.

O principal resultado, entretanto, apareceu na comparação entre o Experimento B e o Experimento D.

O `repartition(16)` introduziu:

```text
RoundRobinPartitioning(16)
```

antes da agregação parcial.

Posteriormente, o `groupBy("group_id")` ainda precisou executar:

```text
hashpartitioning(group_id, 762)
```

Ou seja, o particionamento manual não eliminou o Shuffle necessário à agregação.

Ele adicionou uma redistribuição anterior.

No cenário sem intervenção manual, o Spark conseguiu executar a agregação parcial antes do Shuffle necessário ao `groupBy`, evitando essa etapa adicional.

A principal conclusão do laboratório é:

> **Mais partições não significam necessariamente mais performance. Alterar o particionamento manualmente sem evidência pode introduzir Shuffles adicionais e piorar a execução. O particionamento deve ser tratado como uma decisão de tuning baseada no workload, no plano físico e em medições reais de desempenho.**

O laboratório também reforçou que o número informado em `repartition(N)` representa uma etapa específica do plano e não necessariamente a quantidade de partições utilizada por toda a consulta.

Por fim, embora o `AdaptiveSparkPlan` estivesse presente, o ambiente apresentou apenas o `Initial Plan`. Portanto, qualquer eventual adaptação realizada pelo AQE durante a execução não pôde ser comprovada neste experimento.
