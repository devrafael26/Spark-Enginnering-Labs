## *Spark Engineering Lab #19 — OPTIMIZE*

## Categoria

Delta Lake

## Objetivo

Entender como o comando `OPTIMIZE` reorganiza fisicamente os arquivos de uma tabela Delta, compactando vários arquivos pequenos em arquivos maiores sem alterar o conteúdo lógico da tabela.

## Pergunta

Como o `OPTIMIZE` altera a organização física dos arquivos de uma tabela Delta?

## Experimento

O laboratório foi dividido em cinco etapas:

- **Experimento A:** criar uma tabela Delta e provocar várias pequenas gravações com `append`;
- **Experimento B:** observar o estado da tabela antes do `OPTIMIZE`;
- **Experimento C:** executar o `OPTIMIZE` e analisar as métricas retornadas;
- **Experimento D:** comparar o estado da tabela depois da otimização;
- **Experimento E:** executar o `OPTIMIZE` novamente, sem novos dados, para observar seu comportamento sobre um conjunto de dados já otimizado.

## Dados

Os dados foram gerados artificialmente com `spark.range()`.

A tabela utilizada foi:

```text
workspace.default.lab19_optimize
```

Foram criados inicialmente `100.000` registros e, em seguida, realizadas dez pequenas gravações adicionais de `10.000` registros cada.

Quantidade final:

```text
100.000 registros iniciais
+
10 × 10.000 registros
=
200.000 registros
```

Foram utilizadas também as colunas:

- `category_id`: criada a partir de `id % 10`;
- `value`: criada a partir de `id * 10`.

As várias operações de `append` foram utilizadas propositalmente para produzir um cenário com múltiplos arquivos de dados.

## Transformações

Foram realizadas:

- criação das colunas `category_id` e `value`;
- gravação inicial da tabela em formato Delta;
- dez operações de `append`;
- compactação física dos arquivos por meio de `OPTIMIZE`.

## Action

As gravações com `saveAsTable()` materializaram os dados na tabela Delta.

Posteriormente, os comandos executados por meio de `spark.sql()` realizaram a leitura das informações da tabela e a operação de otimização.

## Comandos de análise

Foram utilizados:

```sql
DESCRIBE DETAIL workspace.default.lab19_optimize
```

para observar principalmente:

- `numFiles`;
- `sizeInBytes`.

Também foi utilizado:

```sql
SELECT COUNT(*)
FROM workspace.default.lab19_optimize
```

para validar que a quantidade lógica de registros permaneceu inalterada.

O próprio resultado do comando:

```sql
OPTIMIZE workspace.default.lab19_optimize
```

foi utilizado como evidência da quantidade de arquivos adicionados e removidos pela operação.

## Código

### Experimento A — Criar a tabela e provocar várias gravações

```python
from pyspark.sql import functions as F

table_name = "workspace.default.lab19_optimize"

spark.sql(f"DROP TABLE IF EXISTS {table_name}")

df_inicial = (
    spark.range(0, 100_000)
    .withColumn("category_id", (F.col("id") % 10))
    .withColumn("value", F.col("id") * 10)
)

(
    df_inicial.write
    .format("delta")
    .mode("overwrite")
    .saveAsTable(table_name)
)

for i in range(10):

    inicio = 100_000 + (i * 10_000)
    fim = inicio + 10_000

    df_append = (
        spark.range(inicio, fim)
        .withColumn("category_id", (F.col("id") % 10))
        .withColumn("value", F.col("id") * 10)
    )

    (
        df_append.write
        .format("delta")
        .mode("append")
        .saveAsTable(table_name)
    )
```

### Experimento B — Observar o estado da tabela antes do OPTIMIZE

```python
spark.sql(f"""
DESCRIBE DETAIL {table_name}
""").display()

spark.sql(f"""
SELECT COUNT(*) AS total_registros
FROM {table_name}
""").display()
```

### Experimento C — Executar o OPTIMIZE

```python
spark.sql(f"""
OPTIMIZE {table_name}
""").display()
```

### Experimento D — Comparar o estado depois do OPTIMIZE

```python
spark.sql(f"""
DESCRIBE DETAIL {table_name}
""").display()

spark.sql(f"""
SELECT COUNT(*) AS total_registros
FROM {table_name}
""").display()
```

### Experimento E — Executar o OPTIMIZE novamente

```python
spark.sql(f"""
OPTIMIZE {table_name}
""").display()

spark.sql(f"""
DESCRIBE DETAIL {table_name}
""").display()
```

## Observações

### Estado da tabela antes do OPTIMIZE

No `DESCRIBE DETAIL`, foram observados:

```text
numFiles    = 25
sizeInBytes = 35188
```

A consulta de contagem retornou:

```text
total_registros = 200000
```

Portanto, antes da otimização, os `200.000` registros da tabela estavam distribuídos em `25` arquivos ativos.

### Resultado do primeiro OPTIMIZE

O comando `OPTIMIZE` retornou, entre suas métricas:

```text
numFilesAdded   = 1
numFilesRemoved = 25
```

No experimento, o `OPTIMIZE` reescreveu o conjunto de arquivos utilizados pelo snapshot atual da tabela:

```text
25 arquivos
     ↓
 OPTIMIZE
     ↓
1 arquivo
```

O termo `numFilesRemoved = 25` não significa que os arquivos antigos foram necessariamente apagados fisicamente do armazenamento naquele momento. Eles deixaram de fazer parte do snapshot atual da tabela após a reescrita. A remoção física de arquivos antigos é um assunto relacionado ao `VACUUM` e às regras de retenção estudadas no Lab 18.

### Estado da tabela depois do OPTIMIZE

Após a execução, o novo `DESCRIBE DETAIL` mostrou:

```text
numFiles    = 1
sizeInBytes = 1641
```

A quantidade de registros continuou sendo:

```text
total_registros = 200000
```

Comparação observada:

| Métrica | Antes | Depois |
|---|---:|---:|
| `numFiles` | 25 | 1 |
| `sizeInBytes` | 35188 | 1641 |
| Registros | 200000 | 200000 |

O resultado mostra que o `OPTIMIZE` alterou a organização física dos arquivos sem alterar o conteúdo lógico da tabela.

A redução de `sizeInBytes` observada faz parte do resultado específico deste experimento. Não deve ser interpretada como uma regra matemática de que reduzir a quantidade de arquivos provoca necessariamente uma redução proporcional do tamanho armazenado.

### Segunda execução do OPTIMIZE

Sem realizar novas gravações, o `OPTIMIZE` foi executado novamente.

O resultado mostrou:

```text
numFilesAdded   = 0
numFilesRemoved = 0
```

O `DESCRIBE DETAIL` permaneceu com:

```text
numFiles    = 1
sizeInBytes = 1641
```

Ou seja, a segunda execução não encontrou arquivos que precisassem ser novamente compactados.

Esse comportamento observado é compatível com a característica documentada de idempotência do bin-packing realizado pelo `OPTIMIZE`: quando ele é executado novamente sobre o mesmo conjunto de dados já otimizado, a segunda execução não produz um novo efeito de compactação.

## O que é documentado oficialmente

A Databricks documenta que:

- múltiplas alterações em uma tabela podem produzir diversos arquivos pequenos, o que pode prejudicar consultas de leitura;
- `OPTIMIZE` reescreve os arquivos de dados para melhorar o layout físico;
- quando não é utilizado liquid clustering nem uma estratégia de colocação como `ZORDER`, a otimização realiza bin-packing;
- o bin-packing é idempotente;
- `OPTIMIZE` não altera os dados lógicos da tabela, portanto leituras antes e depois da operação devem retornar os mesmos resultados;
- o comando retorna estatísticas dos arquivos adicionados e removidos pela operação.

Documentação oficial:

- [Optimize data file layout — Databricks](https://docs.databricks.com/gcp/pt/tables/operations/optimize)
- [OPTIMIZE — Databricks SQL](https://docs.databricks.com/aws/en/sql/language-manual/delta-optimize)
- [Create and manage Delta Lake tables — Optimize a table](https://docs.databricks.com/aws/en/delta/tutorial)

## O que foi observado no laboratório

Neste experimento:

```text
ANTES DO OPTIMIZE

25 arquivos
35.188 bytes
200.000 registros
```

Após o primeiro `OPTIMIZE`:

```text
1 arquivo
1.641 bytes
200.000 registros
```

As métricas da operação mostraram:

```text
numFilesRemoved = 25
numFilesAdded   = 1
```

Na segunda execução, sem novos dados:

```text
numFilesRemoved = 0
numFilesAdded   = 0
```

## Interpretação

As várias gravações realizadas no Experimento A produziram uma tabela suficientemente fragmentada para demonstrar o problema de arquivos pequenos.

O primeiro `OPTIMIZE` compactou os `25` arquivos ativos em `1` novo arquivo, enquanto a quantidade lógica de registros permaneceu em `200.000`.

Como nenhum novo dado foi inserido depois da primeira otimização, a segunda execução não encontrou arquivos que precisassem ser reorganizados, evidenciando no laboratório o comportamento idempotente do bin-packing.

## Conclusão

O laboratório demonstrou que o `OPTIMIZE` atua sobre a organização física dos arquivos de uma tabela Delta.

Antes da otimização, os `200.000` registros estavam distribuídos em `25` arquivos. Após o `OPTIMIZE`, o snapshot atual passou a utilizar apenas `1` arquivo, enquanto a quantidade de registros permaneceu inalterada.

O experimento também mostrou que executar novamente o `OPTIMIZE`, sem novas gravações, não provocou nova reescrita: nenhum arquivo foi adicionado ou removido na segunda execução.

Assim, o principal aprendizado do laboratório é que o `OPTIMIZE` pode reduzir a fragmentação de arquivos de uma tabela Delta por meio de compactação, melhorando o layout físico dos dados sem alterar seu conteúdo lógico.
