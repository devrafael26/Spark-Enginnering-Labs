## *Spark Engineering Lab 18 — VACUUM*

## Categoria

Delta Lake

## Objetivo

Entender como o `VACUUM` atua sobre arquivos de dados de uma tabela Delta que deixaram de ser necessários para o estado atual, como funciona a janela de retenção e qual é a relação entre a remoção física desses arquivos e o Time Travel.

Também foi objetivo do laboratório observar as proteções existentes no Delta Lake para evitar a remoção prematura de arquivos e verificar as limitações encontradas no Databricks Serverless utilizado no experimento.

---

## Pergunta

Como o VACUUM remove arquivos antigos de uma tabela Delta e qual é o impacto da política de retenção sobre o Time Travel?

---

## Conceito

Operações como `UPDATE`, `DELETE`, `MERGE` e outros tipos de escrita podem gerar novos arquivos de dados para representar um novo estado da tabela Delta.

O Transaction Log mantém o histórico das versões da tabela e as referências aos arquivos necessários para representar cada estado.

Assim, um arquivo que deixou de fazer parte do estado atual da tabela não é necessariamente removido imediatamente do armazenamento.

Essa permanência dos arquivos antigos é uma das condições que possibilitam o Time Travel.

Conceitualmente:

```text
Operação de escrita
        ↓
novo estado da tabela
        ↓
novos arquivos podem ser criados
        ↓
arquivos anteriores podem deixar
de fazer parte do estado atual
        ↓
arquivos antigos permanecem
durante a janela de retenção
        ↓
VACUUM
        ↓
remoção física dos arquivos
quando eles se tornam elegíveis
```

Portanto, existe uma diferença importante entre:

```text
UPDATE / DELETE / MERGE
        ↓
alteração lógica do estado da tabela
```

e:

```text
VACUUM
        ↓
remoção física de arquivos de dados
que não precisam mais ser preservados
```

---

## Retenção

Para arquivos de dados removidos logicamente, a propriedade relacionada ao `VACUUM` é:

```text
delta.deletedFileRetentionDuration
```

O valor padrão documentado pela Databricks é:

```text
7 dias
```

ou:

```text
168 horas
```

Isso significa que arquivos que deixaram de ser referenciados não são imediatamente eliminados pelo `VACUUM`.

Eles precisam também satisfazer a política de retenção.

Outra propriedade importante é:

```text
delta.logRetentionDuration
```

Essa propriedade está relacionada à retenção do histórico do Transaction Log e possui valor padrão documentado de:

```text
30 dias
```

Os dois conceitos não devem ser confundidos:

```text
delta.deletedFileRetentionDuration
        ↓
retenção dos arquivos de dados
        ↓
default: 7 dias


delta.logRetentionDuration
        ↓
retenção do histórico do Transaction Log
        ↓
default: 30 dias
```

O `VACUUM` atua principalmente sobre os arquivos de dados.

Os arquivos antigos do `_delta_log` possuem seu próprio processo de retenção e limpeza e não são removidos pelo `VACUUM`.

Para que uma versão antiga continue disponível para Time Travel, precisam continuar disponíveis tanto as informações necessárias no log quanto os arquivos de dados utilizados por aquela versão.

---

## Experimento

O laboratório criou uma tabela Delta e posteriormente executou operações de escrita para gerar diferentes versões da tabela.

Depois foi utilizado o Time Travel para comprovar que um estado anterior ainda podia ser consultado.

Em seguida, foram executados comandos `VACUUM DRY RUN` com diferentes períodos de retenção para investigar quais arquivos poderiam ser removidos.

Por último, foi realizada uma tentativa controlada de reduzir a retenção para `0 HOURS`, com o objetivo de provocar a remoção imediata dos arquivos antigos.

## Código

```python
table_name = "workspace.default.lab18_vacuum"
```

```python

    id INT,

""")
```

```python
spark.sql(f"""

    (1, 'Notebook', 3500.00),
    (2, 'Mouse', 150.00),
```

```python
spark.sql(f"""
```

```python
spark.sql(f"""
```

## Time Travel

Foi consultada a versão `1` da tabela:

```python
spark.sql(f"""
SELECT *
FROM {table_name}
VERSION AS OF 1
ORDER BY id
""").show()
```

### Resultado observado

A consulta retornou corretamente o estado antigo:

```text
1 | Notebook | 3500.00
2 | Mouse    | 150.00
3 | Teclado  | 300.00
```

Mesmo depois das operações posteriores de `UPDATE` e `DELETE`, essa versão ainda pôde ser consultada.

### Evidência

O experimento mostrou que alterar o estado atual da tabela não significa que os arquivos necessários aos estados anteriores sejam imediatamente removidos.

Nesse momento, os arquivos necessários ao Time Travel ainda estavam disponíveis.

---

## VACUUM DRY RUN

Antes de executar qualquer remoção física, foi utilizado:

```python
spark.sql(f"""
VACUUM {table_name} DRY RUN
""").show(truncate=False)
```

### Resultado observado

```text
+----+
|path|
+----+
+----+
```

Nenhum arquivo foi retornado como elegível para remoção.

O `DRY RUN` permite identificar os arquivos que seriam removidos pelo `VACUUM`, sem realizar efetivamente a exclusão.

Como os arquivos do laboratório haviam acabado de ser criados, eles ainda estavam dentro da janela padrão de retenção.

---

## VACUUM com retenção explícita de 168 horas

Também foi executado:

```python
spark.sql(f"""
VACUUM {table_name}
RETAIN 168 HOURS
DRY RUN
""").show(truncate=False)
```

### Resultado observado

Novamente:

```text
+----+
|path|
+----+
+----+
```

Nenhum arquivo estava elegível para remoção.

### Interpretação

```text
Arquivos criados recentemente
        ↓
retenção = 168 horas
        ↓
arquivos ainda estão dentro
da janela de 7 dias
        ↓
nenhum arquivo elegível
        ↓
DRY RUN retorna path vazio
```

Esse resultado é compatível com o funcionamento documentado do `VACUUM`.

## Tentativa de provocar o VACUUM

Para demonstrar fisicamente a remoção dos arquivos antigos e posteriormente verificar o impacto sobre o Time Travel, seria necessário reduzir artificialmente o período de retenção.

Foi tentado:

```python
spark.conf.set(
    "spark.databricks.delta.retentionDurationCheck.enabled",
    "false"
)
```

### Resultado observado

A configuração não estava disponível no ambiente Databricks Serverless utilizado no laboratório.

Portanto, não foi possível desabilitar a verificação de segurança por meio dessa configuração.

---

## VACUUM RETAIN 0 HOURS

Mesmo assim, foi executado um teste utilizando apenas `DRY RUN`:

```python
spark.sql(f"""
VACUUM {table_name}
RETAIN 0 HOURS
DRY RUN
""").show(truncate=False)
```

### Resultado observado

O Delta Lake bloqueou a operação:

```text
DELTA_VACUUM_RETENTION_PERIOD_TOO_SHORT
```

A mensagem informou que o período solicitado era muito curto e poderia causar problemas caso existissem operações de escrita em andamento.

Também indicou duas possibilidades:

```text
desabilitar a verificação de segurança

ou

utilizar retenção mínima de 168 horas
```

---

## Proteção do Delta Lake

O resultado demonstra uma proteção importante do Delta Lake.

Um `VACUUM` com retenção muito curta poderia remover arquivos que ainda estão sendo utilizados por operações como:

```text
INSERT
UPDATE
DELETE
MERGE
OPTIMIZE
```

ou outras operações de longa duração.

Por isso, a Databricks recomenda retenção de pelo menos 7 dias e possui uma verificação de segurança para impedir valores perigosamente baixos.

No laboratório, essa proteção foi observada diretamente através do erro:

```text
DELTA_VACUUM_RETENTION_PERIOD_TOO_SHORT
```

---

## Limitação observada no Databricks Serverless

O objetivo experimental era chegar ao seguinte cenário:

```text
Versão antiga
        ↓
Time Travel funciona
        ↓
VACUUM RETAIN 0 HOURS
        ↓
arquivos antigos removidos
        ↓
Time Travel da versão antiga falha
```

Porém, não foi possível completar essa etapa no ambiente utilizado.

O Databricks Serverless não permitiu alterar a configuração necessária para desabilitar a proteção de retenção.

Assim:

```text
RETAIN 0 HOURS
        ↓
bloqueado pela safety check

e

desabilitar safety check
        ↓
configuração não disponível
no Serverless
```

Portanto, não foi possível provocar artificialmente a remoção imediata dos arquivos antigos.

Essa limitação faz parte da evidência experimental deste laboratório e não altera o comportamento documentado do `VACUUM`.

Foi observado experimentalmente que:

* as operações de escrita geraram diferentes versões da tabela Delta;

## O que está documentado oficialmente

A documentação oficial do Databricks estabelece que:

* o `VACUUM` remove arquivos de dados que não são mais referenciados pelas versões que precisam ser preservadas dentro do período de retenção;
* o período padrão de retenção de arquivos removidos logicamente é de 7 dias;
* `VACUUM DRY RUN` permite visualizar os arquivos candidatos à remoção sem excluí-los;
* executar `VACUUM` pode eliminar a possibilidade de consultar versões antigas através de Time Travel quando os arquivos necessários a essas versões forem removidos;
* existe uma proteção contra períodos de retenção perigosamente curtos;
* o `VACUUM` não é responsável pela limpeza normal dos arquivos do `_delta_log`;
* o período padrão de retenção do histórico do Transaction Log é de 30 dias.

## Relação entre Transaction Log, Time Travel e VACUUM

Os conceitos estudados nos laboratórios anteriores podem ser conectados da seguinte maneira:

```text
Lab 15 — Transaction Log
        ↓
registra os diferentes estados
da tabela Delta e suas referências

Lab 16 — Time Travel
        ↓
utiliza estados anteriores
e seus respectivos arquivos

Lab 17 — MERGE
        ↓
pode produzir um novo estado
da tabela e novos arquivos

Lab 18 — VACUUM
        ↓
remove fisicamente arquivos antigos
quando eles deixam de precisar ser
preservados pela política de retenção
```

Para o Time Travel funcionar, não basta saber que determinada versão existiu.

Também é necessário que os arquivos de dados necessários para reconstruir aquela versão continuem disponíveis.

Conceitualmente:

```text
Transaction Log
        +
arquivos de dados antigos
        ↓
Time Travel possível
```

Após um `VACUUM` remover os arquivos necessários:

```text
referência histórica
        +
arquivos necessários removidos
        ↓
versão antiga não pode mais
ser reconstruída normalmente
```

## Conclusão

O `VACUUM` é uma operação de manutenção do Delta Lake responsável por remover fisicamente arquivos de dados que deixaram de ser necessários pelas versões que precisam ser preservadas dentro da política de retenção.

Operações como `UPDATE`, `DELETE` e `MERGE` alteram logicamente o estado da tabela, mas os arquivos utilizados por estados anteriores podem continuar armazenados para permitir funcionalidades como o Time Travel.

Por padrão, arquivos de dados removidos logicamente possuem uma janela de retenção de 7 dias. Somente depois de se tornarem elegíveis o `VACUUM` pode removê-los.

No experimento, o Time Travel conseguiu acessar corretamente uma versão anterior da tabela. Em seguida, `VACUUM DRY RUN` e `VACUUM RETAIN 168 HOURS DRY RUN` não encontraram arquivos elegíveis, pois todos os arquivos haviam sido criados recentemente.

Para demonstrar a exclusão física imediatamente, foi tentada uma retenção de `0 HOURS`. O Delta Lake bloqueou a operação através da proteção `DELTA_VACUUM_RETENTION_PERIOD_TOO_SHORT`. A configuração que permitiria desabilitar essa proteção também não estava disponível no Databricks Serverless utilizado.

Portanto, **não foi observada diretamente a remoção física dos arquivos**, mas o laboratório demonstrou o funcionamento da janela de retenção, o uso do `DRY RUN`, a proteção contra períodos de retenção perigosamente curtos e a relação conceitual entre `VACUUM` e Time Travel.

O principal conceito consolidado é:

```text
Alterar ou excluir um dado
não significa remover imediatamente
seu arquivo físico.

        ↓

O Delta mantém arquivos antigos
durante a política de retenção.

        ↓

O VACUUM realiza posteriormente
a limpeza física dos arquivos
que se tornam elegíveis.

        ↓

Se esses arquivos forem necessários
para uma versão antiga, essa versão
deixa de estar disponível para
Time Travel após a remoção.
```
