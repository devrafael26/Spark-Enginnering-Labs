## *Spark Engineering Lab 20 - Z-Ordering vs Liquid Clustering*

## Categoria

Delta Lake

## Objetivo

Entender como **Z-Ordering** e **Liquid Clustering** reorganizam o layout físico de tabelas Delta para favorecer **Data Skipping**, reduzindo a quantidade de arquivos e bytes que precisam ser lidos em consultas seletivas.

O laboratório também busca observar, na prática:

- a diferença entre uma tabela sem estratégia específica de layout, uma tabela otimizada com `ZORDER` e uma tabela com Liquid Clustering;
- como o `OPTIMIZE` atua sobre uma tabela com Liquid Clustering;
- o que acontece quando a clustering key é alterada;
- a diferença entre um `OPTIMIZE` normal e um `OPTIMIZE FULL` após a troca da clustering key;
- como `Files read`, `Files pruned`, `Bytes read` e `Bytes pruned` evidenciam Data Skipping.

---

## Pergunta

Como Z-Ordering e Liquid Clustering organizam o layout físico de uma tabela Delta para favorecer Data Skipping?

---

## Experimento

O laboratório foi dividido em cinco experimentos:

- **Experimento A — Baseline:** tabela Delta sem ZORDER e sem Liquid Clustering;
- **Experimento B — ZORDER:** reorganização da tabela por `customer_id`;
- **Experimento C — Liquid Clustering:** clustering por `customer_id`;
- **Experimento D — Alteração da clustering key:** troca de `customer_id` para `product_id`, seguida de `OPTIMIZE` normal;
- **Experimento E — OPTIMIZE FULL:** reclustering completo do histórico utilizando a clustering key atual `product_id`.

O objetivo foi comparar o comportamento de leitura dos arquivos antes e depois das diferentes estratégias de layout.

# Código

## Criação do DataFrame base

```python
from pyspark.sql import functions as F

df_lab20 = (
    spark.range(30_000_000)
    .withColumn(
        "customer_id",
        F.pmod(F.hash(F.col("id")), F.lit(100_000))
    )
    .withColumn(
        "product_id",
        F.pmod(F.hash(F.col("id") * 13), F.lit(10_000))
    )
    .withColumn(
        "order_date",
        F.date_add(
            F.lit("2025-01-01"),
            F.pmod(F.hash(F.col("id") * 7), F.lit(365))
        )
    )
    .withColumn(
        "amount",
        (
            F.pmod(
                F.hash(F.col("id") * 17),
                F.lit(10_000)
            ) / 100
        ).cast("double")
    )
    .select(
        F.col("id").alias("order_id"),
        "customer_id",
        "product_id",
        "order_date",
        "amount"
    )
)

df_lab20.count()
```

# Experimento D — Alteração da clustering key para product_id

## Objetivo do experimento

Observar o comportamento da tabela ao substituir a clustering key:

```text
customer_id
```

por:

```text
product_id
```

e executar um `OPTIMIZE` normal, sem forçar a reescrita completa do histórico.

## Código

Estado da tabela antes da alteração:

```python
spark.sql("""
DESCRIBE DETAIL workspace.default.lab20_liquid
""").show(truncate=False)
```

Alteração da clustering key:

```python
spark.sql("""
ALTER TABLE workspace.default.lab20_liquid
CLUSTER BY (product_id)
""")
```

Verificação:

```python
spark.sql("""
DESCRIBE DETAIL workspace.default.lab20_liquid
""").show(truncate=False)
```

Otimização normal:

```python
spark.sql("""
OPTIMIZE workspace.default.lab20_liquid
""").show(truncate=False)
```

Consulta pela nova clustering key:

```python
spark.sql("""
SELECT *
FROM workspace.default.lab20_liquid
WHERE product_id = 1234
""").show()
```

## Resultado observado

```text
Files read       = 4
Files pruned     = 0

Bytes read       = 60,25 MB
Bytes pruned     = 0 B

Bytes from cache = 0%
Task time        = 1,05 s
```

## Interpretação

A configuração da tabela já havia sido alterada para:

```text
CLUSTER BY (product_id)
```

e um `OPTIMIZE` normal havia sido executado.

Mesmo assim, a consulta por `product_id` apresentou:

```text
4 arquivos lidos
0 arquivos podados
0 bytes podados
```

O resultado é compatível com a característica progressiva do Liquid Clustering: a troca da clustering key não obriga uma reescrita completa e imediata de todos os arquivos históricos.

Os arquivos existentes ainda podiam refletir, total ou parcialmente, o layout produzido anteriormente por `customer_id`.

Uma distinção importante é:

```sql
ALTER TABLE tabela
CLUSTER BY (product_id)
```

**substitui** a configuração anterior.

Isso não significa:

```text
customer_id + product_id
```

As clustering keys não são acumuladas automaticamente.

Para utilizar as duas colunas simultaneamente seria necessário declarar explicitamente:

```sql
ALTER TABLE tabela
CLUSTER BY (customer_id, product_id);
```

Também não existe aqui uma relação de chave primária composta.

Clustering keys são critérios de **organização física dos dados**, e não regras de unicidade ou integridade.

A diferença entre os experimentos D e E foi clara.

### Antes do FULL

```text

Bytes pruned = 0 B
```

### Depois do FULL


Isso não significa que `OPTIMIZE FULL` precise ser executado imediatamente em toda mudança de clustering key.

Em tabelas grandes, essa operação pode ser custosa.

A decisão depende do workload e da necessidade de fazer com que consultas sobre os dados históricos se beneficiem imediatamente da nova organização.

# Observações

## 1. Data Skipping

O Delta Lake utiliza estatísticas por arquivo para identificar arquivos que não precisam ser lidos.

Entre as estatísticas utilizadas estão:

- valores mínimos;
- valores máximos;
- quantidade de valores nulos;
- quantidade total de registros.

Exemplo conceitual:

```text
Arquivo A → customer_id 1 até 1.000
Arquivo B → customer_id 1.001 até 2.000
Arquivo C → customer_id 2.001 até 3.000

Filtro:
customer_id = 1.500
```

O arquivo B é candidato à leitura, enquanto A e C podem ser ignorados pelas estatísticas.

Documentação oficial:

https://docs.databricks.com/aws/pt/tables/data-skipping

---

## 2. ZORDER

Z-Ordering busca colocalizar informações relacionadas nos mesmos conjuntos de arquivos.

Quando uma coluna utilizada frequentemente em filtros possui boa organização física, as estatísticas por arquivo podem se tornar mais seletivas e permitir maior Data Skipping.

Exemplo:

```sql
OPTIMIZE tabela
ZORDER BY (customer_id);
```

O ZORDER pode receber múltiplas colunas:

```sql
OPTIMIZE tabela
ZORDER BY (customer_id, product_id);
```

Nesse caso, a organização considera múltiplas dimensões simultaneamente.

Não deve ser interpretado como um simples:

```sql
ORDER BY customer_id, product_id
```

A documentação também alerta que a eficácia do ZORDER tende a diminuir conforme mais colunas são adicionadas.

Documentação oficial:

https://docs.databricks.com/aws/pt/tables/data-skipping

---

## 3. Liquid Clustering

Liquid Clustering transforma as clustering keys em parte da configuração da tabela.

Exemplo:

```sql
ALTER TABLE tabela
CLUSTER BY (customer_id);
```

Depois:

```sql
OPTIMIZE tabela;
```

Em tabelas com Liquid Clustering habilitado, o `OPTIMIZE` reescreve arquivos para agrupar os dados de acordo com as clustering keys.

A Databricks recomenda atualmente Liquid Clustering em vez de ZORDER para novos layouts de tabela.

Documentação oficial:

https://docs.databricks.com/aws/pt/tables/clustering

https://docs.databricks.com/gcp/pt/tables/operations/optimize

---

## 4. Alterar uma clustering key substitui a configuração anterior

Exemplo:

```sql
CLUSTER BY (customer_id)
```

seguido de:

```sql
ALTER TABLE tabela
CLUSTER BY (product_id);
```

significa:

```text
ANTES
customer_id

DEPOIS
product_id
```

Não significa:

```text
customer_id + product_id
```

Para manter as duas colunas:

```sql
ALTER TABLE tabela
CLUSTER BY (customer_id, product_id);
```

As clustering keys definem organização física e não unicidade.

---

## 5. Layout físico e clustering key configurada não são exatamente a mesma coisa

Um ponto importante observado durante o laboratório foi distinguir:

```text
configuração atual da tabela
```

de:

```text
layout físico atual dos arquivos
```

Ao trocar:

```text
customer_id
```

por:

```text
product_id
```

a configuração da tabela muda imediatamente, mas isso não significa que todos os arquivos históricos sejam instantaneamente reescritos.

Assim, durante uma transição, pode existir:

```text
clustering key atual:
product_id

arquivos históricos:
ainda refletindo total ou parcialmente
o layout anterior por customer_id
```

O benefício de Data Skipping depende do **layout físico efetivamente presente nos arquivos**, e não apenas do nome da clustering key configurada no momento.

---

## 6. OPTIMIZE normal vs OPTIMIZE FULL

Em uma tabela com Liquid Clustering:

```sql
OPTIMIZE tabela;
```

atua de forma incremental sobre o layout.

Já:

```sql
OPTIMIZE tabela FULL;
```

força a otimização completa dos dados existentes segundo as clustering keys atuais.

No laboratório:

```text
D — product_id + OPTIMIZE normal
Files pruned = 0
```

Depois:

```text
E — product_id + OPTIMIZE FULL
Files pruned = 3
```

Isso tornou visível a diferença entre a evolução progressiva do layout e o reclustering completo do histórico.

Documentação oficial:

https://docs.databricks.com/aws/pt/tables/clustering

---

## 7. Múltiplas clustering keys

Liquid Clustering permite trabalhar com mais de uma coluna:

```sql
CLUSTER BY (customer_id, product_id)
```

Nesse cenário, as duas colunas participam da organização do layout físico.

Isso pode alterar as métricas de pruning dependendo do padrão das consultas.

Por exemplo, filtros por:

```sql
WHERE customer_id = ...
```

```sql
WHERE product_id = ...
```

ou:

```sql
WHERE customer_id = ...
  AND product_id = ...
```

podem apresentar comportamentos diferentes.

Esse cenário não foi incluído como experimento principal para evitar acrescentar outra variável à comparação A–E.

---

## 8. Automatic Liquid Clustering

Liquid Clustering também pode operar em modo automático:

```sql
CLUSTER BY AUTO
```

Nesse modo, o Databricks pode escolher e alterar clustering keys com base no workload observado.

A ideia não é simplesmente acumular continuamente novas chaves.

As clustering keys podem evoluir conforme os padrões de consulta mudam.

Documentação oficial:

https://docs.databricks.com/aws/pt/tables/clustering

## 10. Relação com Spark Performance Engineering

Na Fase 2 foram estudados mecanismos como:

- Shuffle;
- Partitions;
- Repartition e Coalesce;
- Broadcast Join;
- Data Skew;
- Cache;

Esses mecanismos tratam principalmente de como o Spark executa o processamento distribuído depois que os dados entram na execução.

Neste laboratório, a otimização acontece antes ou durante a leitura:

```text
Tabela Delta
      ↓
estatísticas por arquivo
      ↓
Data Skipping
      ↓
arquivos irrelevantes são ignorados
      ↓
menos dados entram no processamento
      ↓

agregações, shuffle etc.
```

Portanto, existem diferentes camadas de performance:

```text
LAYOUT FÍSICO
      ↓
reduzir a quantidade de dados lidos

+

EXECUÇÃO SPARK
      ↓
processar eficientemente
os dados que foram lidos
```

# O que está documentado oficialmente

A documentação oficial da Databricks estabelece que:

- Data Skipping utiliza estatísticas por arquivo para ignorar arquivos irrelevantes durante consultas;
- entre essas estatísticas estão valores mínimos, máximos, contagem de nulos e quantidade total de registros;
- Z-Ordering é uma técnica de colocalização de informações relacionadas nos mesmos conjuntos de arquivos;
- os algoritmos de Data Skipping utilizam essa colocalidade para reduzir a quantidade de dados lidos;
- ZORDER pode utilizar múltiplas colunas, mas sua eficácia tende a cair conforme colunas adicionais são incluídas;
- tabelas Delta sem Liquid Clustering podem utilizar `ZORDER BY` durante `OPTIMIZE`;
- em tabelas com Liquid Clustering, `OPTIMIZE` reescreve os arquivos agrupando os dados pelas clustering keys;
- Liquid Clustering permite redefinir clustering keys sem exigir a reescrita imediata dos dados existentes;
- Liquid Clustering foi projetado para permitir que o layout evolua junto com as necessidades analíticas;
- `OPTIMIZE FULL` pode ser utilizado para forçar o reclustering completo dos dados existentes;
- Databricks recomenda Liquid Clustering em vez de ZORDER para novos layouts de tabela.

# Interpretação baseada nas evidências

Os resultados são consistentes com a ideia de que uma organização física alinhada às colunas utilizadas nos filtros pode tornar as estatísticas dos arquivos mais seletivas e aumentar a capacidade de Data Skipping.

No cenário base, nenhum arquivo foi eliminado.

Depois do ZORDER por `customer_id`, arquivos passaram a ser podados.

Com Liquid Clustering por `customer_id`, o `OPTIMIZE` reduziu o número de arquivos de 8 para 4 e a consulta conseguiu eliminar 3 deles.

Ao alterar a clustering key para `product_id`, a configuração da tabela mudou, mas um `OPTIMIZE` normal não resultou, naquele momento, em pruning para a consulta por `product_id`.

Após `OPTIMIZE FULL`, a consulta pela nova chave passou a eliminar 3 dos 4 arquivos.

Essa diferença evidencia que:

> **alterar a clustering key e reclusterizar completamente o histórico são operações conceitualmente distintas.**

Também ficou evidente que o benefício de uma clustering key não deve ser analisado apenas pelo fato de ela estar configurada na tabela.

O fator determinante para Data Skipping é o **layout físico efetivamente produzido nos arquivos e as estatísticas disponíveis para a consulta**.

---

# Conclusão

O laboratório demonstrou que Z-Ordering e Liquid Clustering atuam sobre o **layout físico dos dados**, buscando reduzir o volume que precisa ser lido antes que o restante do processamento Spark aconteça.

A baseline apresentou:

```text
8 arquivos lidos
0 arquivos podados
```

Depois de ZORDER por `customer_id`:

```text
1 arquivo lido
2 arquivos podados
97,76 MB podados
```

Com Liquid Clustering por `customer_id`:

```text
1 arquivo lido
3 arquivos podados
136,28 MB podados
```

Ao alterar a clustering key para `product_id` e executar um `OPTIMIZE` normal:

```text
4 arquivos lidos
0 arquivos podados
```

Após:

```sql
OPTIMIZE ... FULL
```

foram observados:

```text
1 arquivo lido
3 arquivos podados
147,04 MB podados
```

O experimento também mostrou que:

- alterar `CLUSTER BY (customer_id)` para `CLUSTER BY (product_id)` **substitui** a clustering key anterior;
- as chaves não são acumuladas automaticamente;
- múltiplas clustering keys precisam ser declaradas explicitamente;
- clustering keys não representam chaves primárias ou regras de unicidade;
- a configuração atual de clustering e o layout físico atual dos arquivos não devem ser tratados como exatamente a mesma coisa;
- a mudança da clustering key pode ocorrer sem reescrita imediata de todo o histórico;
- `OPTIMIZE FULL` permite alinhar completamente os dados históricos às clustering keys atuais quando isso for necessário;
- essa flexibilidade é uma das diferenças importantes entre Liquid Clustering e uma reorganização explícita por ZORDER.

O principal aprendizado do laboratório foi:

> **performance de leitura não depende apenas da quantidade de arquivos, mas também de como os dados estão distribuídos dentro desses arquivos e de quão úteis são suas estatísticas para Data Skipping.**

Liquid Clustering evolui esse gerenciamento de layout ao permitir que a estratégia de organização física da tabela seja alterada e evolua ao longo do tempo sem exigir, em toda mudança, uma reescrita completa e imediata do histórico.
